为什么是这四个

这四个技术不是随机拼盘——它们分别站在后端系统的四个基础位置上：什么时候跑、东西怎么找到、服务之间怎么说话、数字随时间怎么存。

◇
先钉住项目：本仓库是 zhipin-apm（性能 / 质量监控平台）。前端 SDK 把 JS 错误、白屏、页面性能等统计点打上来，后端要接住、存住、聚合出曲线、到点告警——四周用的正是这四块基建。

01
调度 · SCHEDULING

xxl-job · 分布式任务调度

分布式环境里的 setInterval + cron——解决「多台机器时，到点的任务由谁来跑、怎么保证只跑一次、跑失败了怎么办」。

≈ 6 min
①是什么 · 解决什么问题≈ 1 min
单机 cron 在多副本部署下会失控：3 个副本都配了同一个定时任务 → 同一件事被执行 3 遍；某台挂了也没人知道。 xxl-job 的答案：把「决定何时跑、谁来跑」和「真正干活」拆成两个独立角色，中间用 MySQL 做共享状态。
②核心概念（只讲 3 个）≈ 1.5 min
概念 1调度中心 / 执行器分离

调度中心 admin：独立 Web 管理台，管任务配置、按 cron 到点触发、选机器、记日志。执行器 Executor：嵌在业务应用里的 SDK，被动接收 HTTP 触发，跑 @XxlJob 方法。中间用 MySQL 存任务定义、注册表、日志——集群唯一的「事实来源」。

概念 2执行器组 + 心跳

同一应用的多个副本以相同 AppName 注册，自动聚成一个「组」；每 30 秒写一次心跳，90 秒没心跳就被摘除。组是一个「看不见的集群」。

概念 3路由策略

一次触发，从组里选一台执行：轮询 / 随机 / 故障转移……例外是分片广播：每台都收到、各带不同分片号。本仓 FE 相关任务以「选一台执行」为主，分片广播知道概念即可。

⚠ 类比在这里失效 · 别带着错误心智模型走
  • 定时器是单进程、内存态：页面关了就没了，也不存在「谁来跑」的选择。xxl-job 的调度方和执行方是两个进程甚至两台机器，靠 HTTP + MySQL 通信——所以才有注册、心跳、路由这一整套东西。
  • 投递语义不同：setTimeout 错过就错过了；xxl-job 是 at-least-once——重试与补触发意味着任务可能执行不止一次，任务代码必须幂等（对应前端的「按钮防连点」，但这层在后端永远省不掉）。
  • 「组」是看不见的：谁在跑任务，以 admin 的注册地址为准，而不是你以为部署了哪些实例。
④典型场景 · 高频踩坑≈ 1.5 min
本仓落点 · zhipin-apm-schedule 执行器在模块 zhipin-apm-schedule（XxlJobConfig 注册 XxlJobSpringExecutor；admin 地址 / AppName 等走配置中心）。全是前端 / 统计相关任务： feOneMinuteAlarm / feFiveMinuteAlarm（查 Influx fe_error_v2_metrics 推 FE 告警）、 preCreateTomorrowEsIndex（预建明日 JS 错误 / 白屏 ES 索引）、 removeExpiredApmEsData（按 TTL 清理过期明细）、 calFeIssueData / sendFeIssueData、calMiniAppPageViewData、jsMonitorAlarm。
踩坑 · 幽灵执行器（真实事故） 注册只看「能不能连上同一套 admin + MySQL」，不看部署在哪。同事本地跑着旧版本服务也注册进了同一个执行器组，轮询路由下触发在新代码（QA）和旧代码（本地）之间交替——表现为「配置明明改了，旧行为隔一次出现一次」。 教训：判断「谁在跑任务」的唯一权威来源是 admin 的注册地址列表和调度日志，不是 k8s 的 Pod 列表。
踩坑 · 分片广播 ≠ 天然安全（一句带过） 代码里不读 shardIndex，每台机器就会把全量逻辑各跑一遍。广播必须配合分片编码。本仓 FE 任务几乎不依赖这套，知道有这坑即可。
02
搜索 · SEARCH

Elasticsearch · 全文搜索

MySQL 擅长「按条件精确查一条记录」，ES 擅长「在一堆文本里搜出相关内容，并按相关度排序」——基于倒排索引的分布式搜索引擎。

≈ 6 min
①是什么 · 解决什么问题≈ 1 min
数据库自带的 LIKE '%关键词%' 是「拿关键词去每一行里找」——数据量大了必然全表扫描，更没有中文分词、纠错、相关度排序。 在本仓的角色：ES 存的是前端上报的 action 明细（某次 JS 错误的原文、白屏现场、网络错误上下文……），不是业务主库，也不是画曲线的地方。
倒排索引 · 先分词，再按词查文档
原始文档（JS 错误）
doc1: "Cannot read property of undefined"
doc2: "TypeError: undefined is not a function"
doc3: "Cannot read property of null"
→
倒排索引（写入时就建好）
Cannotdoc1, doc3
readdoc1, doc3
undefineddoc1, doc2
TypeErrordoc2

搜「Cannot read」→ 查表直接命中 doc1 / doc3，全程不扫原文。

②核心概念（只讲 3 个）≈ 1.5 min
概念 1倒排索引

写入时就完成分词、建好「词 → 文档列表」。查询成本只和命中的词有关，与总数据量基本无关——这是和 LIKE 的本质区别。

概念 2文档模型

Index ≈ 表，Document ≈ 一行（就是一个 JSON 对象），Mapping ≈ 表结构——核心是定义「每个文本字段怎么分词」，中文场景配 ik 分词器。

概念 3分片 + 副本

一个 Index 拆成多个 Shard 散到不同节点并行处理——水平扩展的关键；Replica 保证节点挂了数据还在，还能分摊查询。

③前端类比≈ 2 min
前端类比 · 先建立熟悉感
前端
Array.filter + sort（带打分）
≈
Elasticsearch
预建索引、分布式的超级过滤器
一句话记忆：ES = 预先建好索引、天生分布式的「超级 Array.filter + 打分排序」。
前端 · 查询写法
match ≈ 搜索框 · term ≈ === · range ≈ >= <= · bool ≈ && || !
≈
ES · Query DSL
用 JSON 写查询条件（REST API 调用）
所有操作都是 HTTP REST——和前端调接口一模一样，只是请求体是 JSON。
⚠ 类比在这里失效 · 别带着错误心智模型走
  • filter 每次全量扫一遍；ES 靠的是写入时预建的倒排索引——成本在写入侧已经付过了。
  • filter 只回答「匹配不匹配」；ES 还给每条结果打相关度分（BM25）并排序——「有多匹配」是前端过滤里没有的维度。
  • 一致性不同：ES 是近实时（写入后约 1 秒才能搜到），且没有事务——所以 ES 永远不当主数据库用：上报事件先经 Kafka，再由消费者写入 ES——ES 是「用来检索明细的副本」。
  • text vs keyword 是前端没有的概念：text 会分词（用于全文搜），keyword 不分词（用于精确匹配）——对 text 字段做精确匹配会查不到。
④典型场景 · 高频踩坑≈ 1.5 min
本仓存什么 · 读写与索引时钟 JS 错误、白屏、页面访问、接口监控等前端 action 明细；admin 的错误列表 / 白屏详情从这里查。 索引按日滚动：{prefix}&{action}&{yyyyMMdd}，例 apm_action_js_error&action_js_monitor&20260903。 读写分离：esReadClient / esWriteClient。与调度联动：preCreateTomorrowEsIndex 预建、removeExpiredApmEsData 按 TTL 清理——索引的「时钟」由 xxl-job 拨。 你在 APM 后台打开某条 JS 错误详情——背后就是按 app、时间、action 条件去 ES 捞文档。
踩坑 · Mapping 只能加不能改 字段类型一旦建好无法修改，改类型要重建索引、重新导数据。第一天就要规划好（上报字段新增尤其要小心）。
踩坑 · 深度分页 from + size 超过 1 万条性能急剧下降。正确姿势是 search_after 游标分页——类似前端无限滚动用 cursor 而不是 offset。
03
消息 · MESSAGING

Kafka · 分布式消息系统

把你熟悉的发布订阅模型搬到服务器集群上，还给每条消息上了「持久保险」——写盘、可重放、多个消费者各自独立消费。

≈ 6 min
①是什么 · 解决什么问题≈ 1 min
三件事：解耦（上报入口不需要知道谁要写 ES、谁要算错误曲线）、削峰（高峰期 SDK 狂打，先落盘排队，下游按自己的速度消费）、可回放（某个消费者挂了重启，从断点继续读）。 如果说 mitt / EventBus 是「进程内、内存里、用完即丢」的事件总线，Kafka 就是它的跨服务器、持久化版本。
②核心概念（只讲 3 个）≈ 1.5 min
概念 1Topic

一类消息的频道。本仓主事件流是 boss.arch.monitor.apm_action（前端 / App 各类 action 上报都进这里；本分享只盯前端统计点）。

概念 2Partition + Offset

一个 Topic 拆成多个分区并行读写提吞吐，分区内严格有序。Offset 是消费者的「已读游标」——重启后从游标继续。

概念 3Consumer Group

同组内多个实例分摊消息（负载均衡）；不同组之间各自拿到完整一份（广播）。一份上报消息天然同时服务多个下游。

⚠ 类比在这里失效 · 本模块重点，逐个说清
  • 持久化：EventBus 是内存态，页面刷新事件历史就没了；Kafka 消息写磁盘、按时间保留（比如 7 天），任何人可在任意时间回放这段历史。
  • 消费者组：前端是「谁 on 谁收到」；Kafka 的「组」引入组内分摊——同组 3 个实例平分分区，像多个 worker 分工。「组」这个负载均衡单位前端完全没有对应物。
  • 分区：前端事件没有「分片并行」。Kafka 靠分区提吞吐，代价是只有分区内有序——要保证同一页面 / 同一会话相关消息有序，需要用稳定 key 路由到同一分区。
  • 不是请求-响应：不像 axios 等返回值，Kafka 是「发完就不管」；想要结果，得让消费者处理完再发一条新消息（或走别的查询路径）。
④典型场景 · 高频踩坑≈ 1.5 min
本仓 · Producer → 多消费组 FE SDK → ActionLogController（如 /api/zpApm/actionLog/fe/common.json）→ ActionKafkaClient → Topic boss.arch.monitor.apm_action。 同 Topic 多消费组 = 「广播」的活例子——新增一个下游消费组，上报代码一行都不用改。下游还有指标 Topic boss.arch.apm.metrics_log（事件 Topic 与指标 Topic 是两跳）。
消费组干什么
apm.action.listener业务落库（页面记录、Issue 相关处理等）
apm.action.es.listener写 ES 明细（JS 错误 / 白屏等索引）
apm.metrics（compactor）内存聚合 → 再发到 metrics_log → calculator 写 Influx
踩坑 · 消息会重复 投递语义是 at-least-once：网络抖动、消费者重启都可能导致同一条上报被处理两次——消费者必须幂等（监控语境下：重复上报可能让错误次数偏高，聚合侧要能扛）。
踩坑 · 顺序性只在分区内 不做 key 路由，同一页面连续几次相关上报可能散在不同分区被乱序处理。需要顺序时，用稳定业务 ID 做消息 key。
04
时序 · TIME-SERIES

InfluxDB · 时序数据库

专门存「随时间不断产生的一串数值」——每分钟 JS 错误量、H5 加载耗时。与 ES 分工：Influx 画曲线，ES 查 stack / 原文。

≈ 6 min
①是什么 · 解决什么问题≈ 1 min
和业务数据库的本质区别：数据几乎只写不改、批量写入、查询几乎都是「某个时间范围内的聚合」（平均 / 最大 / 求和）。 与 ES 在本仓的分工（务必讲清）：Influx 画「每分钟错误量 / 耗时曲线」；ES 查「这条错误的 stack / 原文」——admin 看板就是这么拆的。
②核心概念（只讲 3 个）≈ 1.5 min
概念 1数据模型四件套

一条数据 = { measurement, tags, fields, timestamp }。本仓例：measurement fe_error_v2_metrics；tags（有索引）如 app_key、error_type；fields（无索引）如 count、tp95。

概念 2Series 基数

一个 series = measurement + tags 的唯一组合。InfluxDB 最重要的性能概念——90% 的性能问题源于此（见踩坑）。

概念 3保留策略 SHORT / LONG

本仓封装了 SHORT / LONG 两套客户端——细粒度（分钟 / 五分钟 / 小时）走 SHORT（约 3 个月），天 / 月级汇总走 LONG（约 2 年），由 time_slice 决定。过期自动淘汰，不必手写清理脚本。

⚠ 类比在这里失效 · 别带着错误心智模型走
  • 量级不同：前端埋点是「采几个点、画条曲线」；TSDB 面对的是每秒成千上万点的高频写入——所以一切设计围绕写入吞吐（批量、只追加、自动过期）。
  • series 基数爆炸是前端没有对应物的概念：把 userId、traceId、甚至未归一化的完整 URL 这种「每个值都不同」的字段放进 tag，series 会冲到百万级。高基数值放 field，tag 只放 app_key、time_slice、有限枚举的 error_type。
  • 查询习惯不同：任何查询都必须带时间范围，否则等于全表扫描——这是最常见的超时事故来源。
④典型场景 · 高频踩坑≈ 1.5 min
本仓 measurement · 前端统计点 fe_error_v2_metrics（FE 错误量，feOneMinuteAlarm 的数据源）、 fe_performance_metrics / h5_load_time_metrics、 fe_blank_screen_metrics、 fe_page_access_metrics / fe_region_error_metrics、 fe_issue_metrics（由 calFeIssueData 写入）。 典型 tags：app_key、time_slice、url、type / sub_type、stable_sig。 admin 错误趋势图读 Influx；点进某条错误看 stack 读 ES——同一条业务链路的两种读法。
踩坑 · 高基数值进 tag userId / traceId / 未归一化 URL 当 tag → series 爆炸 → 写入查询全面劣化。设计 FE 统计维度时就要想清楚「什么能当 tag」。
踩坑 · 查询超时 不带时间范围、或只用 field 条件过滤（不走索引）→ 全表扫描超时。排查第一步：缩小时间范围 + 改用 tag 过滤。
收尾 · 1–2 分钟

用「前端 JS 错误」把四个模块各就各位

四个基础设施不是孤立的工具，而是各司其职地长在同一条上报链路上。

  1. KafkaFE SDK 上报 → 写入 Topic

    一条 JS 错误经 server 写入 Topic boss.arch.monitor.apm_action——消息层负责上报与下游解耦，发完不等回复。

  2. Elasticsearch消费组写日索引明细

    消费组 apm.action.es.listener 写入日索引（如 apm_action_js_error&action_js_monitor&20260903）——搜索层留下可检索的明细原文。

  3. InfluxDB另一路聚合写曲线

    compactor 聚合并转发到 metrics_log → calculator 写入 measurement fe_error_v2_metrics——时序层画出每分钟错误量。

  4. xxl-job到点告警 + 索引时钟

    feOneMinuteAlarm 到点查 Influx 做告警；preCreateTomorrowEsIndex / removeExpiredApmEsData 负责索引生命周期——调度层驱动告警与数据时钟。

  5. admin 看板 · 趋势 + 详情

    你在 admin 上看趋势（Influx）再点开详情（ES）——四块基建各就各位。

带走的三句话

它们都是「前端的升级版」

定时器、filter、EventBus、埋点曲线——前端都有原型；后端基础设施只是把它们变成多机、持久、容错的版本。

为此多了三件新事

选一台机器来跑（调度 / 分区 / 路由）、可能重复所以必须幂等（at-least-once）、数据有同步延迟（近实时 / 异步消费）。

以后遇到新中间件的方法

先问「它解决前端的哪个问题」，再问「为分布式多了哪些概念」——今天的四个模块就是这个方法的四次演练。
