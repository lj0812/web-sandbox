# 后端基础设施认知地图 —— 前端团队技术分享大纲

> **时长**：20–30 分钟（不含 Q&A）
> **听众**：有 Vue3/JS 经验、正在或即将接触 Java 后端、对中间件完全陌生的前端工程师
> **目标**：用「调度 / 搜索 / 消息 / 时序数据」四个角色，建立"后端工程师日常在用什么"的认知骨架
> **讲法约定**：四个模块严格走同一节奏 —— ① 是什么 → ② 核心概念 → ③ 前端类比（含"类比在哪里失效"）→ ④ 场景/踩坑。开场先给骨架，收尾用一条业务链路把四块串回来。
> **例子约定**：全文场景一律取自本仓 **前端上报 / 统计点**（JS 错误、白屏、H5 耗时、FE 告警等），不引入客户端侧心智负担。

## 〇、开场：为什么是这四个（1–2 分钟）

**核心信息一句话**：这四个技术不是随机拼盘，它们分别站在后端系统的四个基础位置上——**什么时候跑（调度）、东西怎么找到（搜索）、服务之间怎么说话（消息）、数字随时间怎么存（时序）**。

- **先钉住项目**：本仓库是 **zhipin-apm（性能/质量监控平台）**。前端 SDK 把 JS 错误、白屏、页面性能等统计点打上来，后端要接住、存住、聚合出曲线、到点告警——四周用的正是这四块基建。
- 先给听众一张"骨架图"：业务代码（Spring Boot 应用）只占中间一小块，四周全是基础设施。对照本仓，中间那块大致拆成这些可部署服务：
  - **`server`**：上报入口（如 `/api/zpApm/actionLog/...`）
  - **`consumer`**：消费事件 → 落业务库 / **写 ES 明细**
  - **`metrics-compactor` → `metrics-calculator`**：聚合后 **写 InfluxDB**
  - **`schedule`**：**xxl-job 执行器**（告警、索引预建/过期清理、日统计）
  - **`admin`**：看板——Influx 看趋势，ES 查明细
- 管道一句话（画在骨架旁）：  
  **`FE SDK → server → Kafka →（并行）ES 明细 + Influx 曲线 → schedule 告警/清理 → admin`**
- 四角色在"监控语境"里各自站哪：
  - **调度层**：总有些事要"到点自动做"——FE 分钟级告警、明日 ES 索引预建、过期明细清理
  - **搜索层**：总有些数据要"按内容找"——某条 JS 错误的 stack、白屏现场
  - **消息层**：总有些服务要"通知别人但不想等回复"——上报入口只负责入队，写 ES / 聚合指标各走各的消费组
  - **时序层**：总有些数字在"不停地产生"——每分钟错误量、H5 加载耗时 TP 分位
- 再给一条主线（贯穿全场的钩子）：**这四样东西，前端其实都有"单进程、内存版"的原型**——`setInterval`、搜索框 `filter`、`mitt`/EventBus、埋点监控曲线。后端做的事，就是把它们升级成"分布式、持久化、出了故障还能活"的版本。带着这个视角听，每个模块都只需要补"升级过程中多出来的那几个概念"。
- 预告节奏：每个模块四段式，听到第三段"前端类比"时可以主动对照自己的心智模型。

## 一、xxl-job · 分布式任务调度（≈6 分钟）

### 1. 是什么 / 解决什么问题
- 一句话：**分布式环境里的 `setInterval` + cron**——解决"多台机器时，到点的任务由谁来跑、怎么保证只跑一次、跑失败了怎么办"。
- 单机 `cron` 的问题：服务部署了 3 个副本，每台都配同样的定时任务 → 同一件事被执行 3 遍；某台挂了也没人知道。xxl-job 就是把"决定何时跑"和"真正干活"拆成两个独立角色来管。

### 2. 核心概念（3 个）
1. **调度中心（admin）与执行器（Executor）分离**：这是理解一切行为的前提。
   - 调度中心 = 独立的 Web 管理台：管任务配置、按 cron 到点触发、选机器、记日志、发告警。
   - 执行器 = 嵌在业务应用里的一个 SDK：被动接收调度中心的 HTTP 触发，跑具体的 `@XxlJob` 方法。
   - 中间用 MySQL 存任务定义、注册表、日志——是集群唯一的"事实来源"。
2. **执行器组 + 注册心跳**：同一个应用的多副本以相同 AppName 注册，自动聚成一个"组"；每 30 秒写一次心跳，90 秒没心跳就被调度中心摘除。
3. **路由策略**：一次触发，从组里**选一台**执行（轮询/随机/故障转移……）；例外是"分片广播"——每台都收到，但各带不同分片号，用于多机并行分摊。**本仓 FE 相关任务以「选一台执行」为主**，分片广播知道概念即可，不必展开。

### 3. 前端类比
- **类比**：
  - 整体 ≈ **CI/CD**：admin 是 GitHub Actions 的控制台+调度服务，执行器是你挂在机房里的 self-hosted runner——平台决定哪个 runner 接单，runner 只管干活并回报结果。
  - 路由策略 ≈ 负载均衡：轮询/随机/故障转移这些名字和 Nginx upstream 一一对应。
  - 时间环调度 ≈ 浏览器事件循环：每一秒只处理"这一秒到期"的任务队列。
  - 阻塞策略 ≈ 前端请求管理："上一次还没跑完，新触发又来了"的三种处理——串行排队 / 丢弃后续（≈ SWR 请求去重）/ 覆盖之前（≈ `AbortController.abort()`）。
- **类比失效的地方（重点提醒）**：
  - 前端定时器是"单进程、内存态"：页面关了就没了，也不存在"谁来跑"的选择。xxl-job 的调度方和执行方**是两个进程甚至两台机器**，中间靠 HTTP + MySQL 通信，所以才有注册、心跳、路由这一整套东西。
  - 投递语义不同：`setTimeout` 错过就错过了；xxl-job 是 **at-least-once**——重试和补触发意味着任务**可能被执行不止一次**，所以任务代码必须幂等（前端对应的经验是"按钮防连点"，但后端这层幂等永远省不掉）。
  - "组"是个看不见的集群：谁在跑任务，以 admin 里的注册地址为准，而不是你以为部署了哪些实例（见踩坑）。

### 4. 典型场景 & 踩坑
- **本仓落点**：执行器在模块 **`zhipin-apm-schedule`**（`XxlJobConfig` 注册 `XxlJobSpringExecutor`；admin 地址 / AppName 等走配置中心）。
- **场景（全是前端 / 统计相关）**：
  - `feOneMinuteAlarm` / `feFiveMinuteAlarm`：到点查 Influx `fe_error_v2_metrics`，命中规则就推 FE 告警（呼应模块四）。
  - `preCreateTomorrowEsIndex`：预建明日 JS 错误 / 白屏等 ES 索引（呼应模块二）。
  - `removeExpiredApmEsData`：按 TTL 清理过期 action 明细。
  - `calFeIssueData` / `sendFeIssueData`：FE Issue 日统计写入 Influx 并推送。
  - `calMiniAppPageViewData`：小程序 PV 类聚合统计。
  - `jsMonitorAlarm`：JS 监控告警。
- **踩坑·幽灵执行器（真实事故）**：注册只看"能不能连上同一套 admin + MySQL"，不看部署在哪。同事本地跑着旧版本服务也注册进了同一个执行器组，轮询路由下触发在新代码（QA 环境）和旧代码（本地）之间交替——表现为"配置明明改了，旧行为隔一次出现一次"。**教训：判断"谁在跑任务"的唯一权威来源是 admin 的注册地址列表和调度日志，不是 k8s 的 Pod 列表。**
- **踩坑·分片广播 ≠ 天然安全**（通用知识，一句带过）：代码不读 `shardIndex`，每台机器就会把全量逻辑各跑一遍——广播必须配合分片编码。本仓 FE 任务几乎不依赖这套，知道有这坑即可。

## 二、Elasticsearch · 搜索（≈6 分钟）

### 1. 是什么 / 解决什么问题
- 一句话：**基于倒排索引的分布式全文搜索引擎**。MySQL 擅长"按条件精确查一条记录"，ES 擅长"在一堆文本里搜出相关内容，并按相关度排序"。
- 为什么数据库自带的 `LIKE '%关键词%'` 不行：全表扫描扛不住数据量，更没有中文分词、纠错、相关度排序。
- **在本仓的角色**：ES 存的是前端上报的 **action 明细**（某次 JS 错误的原文、白屏现场、网络错误上下文……），不是业务主库，也不是画曲线的地方。

### 2. 核心概念（3 个）
1. **倒排索引**：提前把"每个词出现在哪些文档里"整理成一张表，查询时按词查文档，而不是拿关键词去每行里找。这是"搜索为什么快"的全部答案。
2. **文档模型**：Index ≈ 表，Document ≈ 一行（就是一个 JSON 对象），Mapping ≈ 表结构——其中最重要的是定义"每个文本字段怎么分词"，直接决定搜索效果；中文场景通常配 ik 分词器。
3. **分片 + 副本（Shard / Replica）**：一个 Index 拆成多个分片散到不同节点并行处理，这是水平扩展的关键；副本保证节点挂了数据还在，还能分摊查询。

### 3. 前端类比
- **类比**：
  - 整体 ≈ **"预先建好索引、能分布式的超级 `Array.filter` + 打分排序"**。
  - Query DSL ≈ 用 JSON 写查询条件，和 SQL/过滤逻辑一一对应：`match` ≈ 搜索框全文搜、`term` ≈ `===` 精确匹配、`range` ≈ `>= <=`、`bool` 的 must/should/must_not ≈ `&& / || / !`。
  - 所有操作都是 HTTP REST API——和前端调接口一模一样，只是请求体是 JSON。
- **类比失效的地方（重点提醒）**：
  - `Array.filter` 每次都**全量扫一遍**；ES 靠的是**提前建好的倒排索引**，写入时就付出了分词建索引的成本。
  - `filter` 只回答"匹配不匹配"；ES 还会给每条结果**打相关度分（BM25）并排序**——"有多匹配"是前端过滤里没有的维度。
  - 一致性不同：ES 是**近实时（NRT）**——写入后约 1 秒才能搜到，且**没有事务**。所以 ES 永远不当主数据库用：上报事件先经 Kafka，再由消费者写入 ES——ES 是"用来检索明细的副本"。
  - `text`（会分词，用于全文搜）和 `keyword`（不分词，用于精确匹配）之分是前端没有的概念：对 `text` 字段做精确匹配会查不到。

### 4. 典型场景 & 踩坑
- **本仓存什么**：JS 错误、白屏、页面访问、接口监控等前端 action 明细；admin 的错误列表 / 白屏详情从这里查。
- **索引命名**（按日滚动）：`{prefix}&{action}&{yyyyMMdd}`  
  - 例：`apm_action_js_error&action_js_monitor&20260903`  
  - 白屏：`apm_action_blank_screen&...`  
  - 非独立 action 可能落到 `apm_action&common_index&yyyyMMdd`
- **读写分离**：`esReadClient`（查）/ `esWriteClient`（写）——读、写可以指向不同集群 URI，搜索层也会拆读写。
- **与调度联动**：`preCreateTomorrowEsIndex` 提前建好明日索引；`removeExpiredApmEsData` 按 TTL 删过期数据——索引的"时钟"由 xxl-job 拨。
- **场景**：你在 APM 后台打开某条 JS 错误详情——背后就是按 app、时间、action 条件去 ES 捞文档，而不是扫 MySQL。
- **踩坑**：
  - Mapping 一旦建好，字段类型**不能改只能加**，改类型要重建索引重新导数据——第一天就要规划好（上报字段新增尤其要小心）。
  - 深度分页（`from + size` 超 1 万条）性能急剧下降，要用 `search_after` 游标分页——类似前端无限滚动用 cursor 而不是 offset。

## 三、Kafka · 消息（≈6 分钟）

### 1. 是什么 / 解决什么问题
- 一句话：**分布式、持久化的消息系统**——把前端熟悉的发布订阅模型搬到服务器集群上，还给每条消息上了"持久保险"。
- 解决三件事：**解耦**（上报入口不需要知道谁要写 ES、谁要算错误曲线）、**削峰**（高峰期 SDK 狂打，先落盘排队，下游按自己的速度消费）、**可回放**（某个消费者挂了重启，从断点继续读）。

### 2. 核心概念（3 个）
1. **Topic**：一类消息的频道。本仓主事件流是 `boss.arch.monitor.apm_action`（前端 / App 各类 action 上报都进这里；本分享只盯前端统计点）。
2. **Partition（分区）+ Offset（偏移量）**：一个 Topic 拆成多个分区并行读写，提升吞吐；分区内消息严格有序。Offset 是消费者的"已读游标"——记录读到第几条了，重启后从游标继续。
3. **Consumer Group（消费者组）**：同组内多个实例**分摊**消息（负载均衡）；不同组之间**各自拿到完整一份**（广播）。一份上报消息天然同时服务"多个下游"。

### 3. 前端类比
- **类比**：
  - `emitter.emit('js:error', data)` ≈ `producer.send("boss.arch.monitor.apm_action", data)`；`emitter.on(...)` ≈ `@KafkaListener(topics=...)`。Topic ≈ 事件名，消息体 ≈ 事件 payload。
- **类比失效的地方（本模块重点，逐个说清）**：
  - **持久化**：mitt/EventBus 是内存态，页面刷新、组件销毁，事件历史就没了；Kafka 消息**写磁盘、按时间保留**（比如 7 天），任何人可在任意时间回放这段历史。
  - **消费者组**：前端是"谁 `on` 谁收到"，多个监听器各收一份；Kafka 的"组"引入了**组内分摊**——同组 3 个实例平分分区，像多个 worker 分工处理一份任务队列。"组"这个负载均衡单位前端完全没有对应物。
  - **分区**：前端事件没有"分片并行"概念。Kafka 靠分区提吞吐，代价是**只有分区内有序**——要保证"同一页面 / 同一会话相关消息有序"，需要用稳定 key 路由到同一分区。
  - **不是请求-响应**：`axios` 发出去要等返回值；Kafka 是"发完就不管"，想要结果得让消费者处理完再发一条新消息（或走别的查询路径）。

### 4. 典型场景 & 踩坑
- **Producer（本仓）**：FE SDK → `ActionLogController`（如 `/api/zpApm/actionLog/fe/common.json`）→ `ActionKafkaClient` → Topic **`boss.arch.monitor.apm_action`**。
- **同 Topic 多消费组 = 文档里「广播」的活例子**（讲透这一条就够）：
  | 消费组 | 干什么 |
  |---|---|
  | `apm.action.listener` | 业务落库（页面记录、Issue 相关处理等） |
  | `apm.action.es.listener` | 写 ES 明细（JS 错误 / 白屏等索引） |
  | `apm.metrics`（compactor） | 内存聚合 → 再发到 **`boss.arch.apm.metrics_log`** → calculator 写 Influx |
- **下游 Topic（串到时序）**：`boss.arch.apm.metrics_log`（聚合后的指标流）；数值类还有 `boss.arch.apm.app_metrics_log` 等——知道"事件 Topic"和"指标 Topic"是两跳即可。
- **场景一句话**：前端打上来一条 JS 错误，入口只负责入队；写 ES、算分钟错误量互不阻塞——新增一个下游消费组，上报代码一行都不用改。
- **踩坑**：
  - 消息投递是 **at-least-once**：网络抖动、消费者重启都可能导致同一条上报被处理两次——**消费者必须幂等**（监控语境下：重复上报可能让错误次数偏高，聚合侧要能扛）。
  - 顺序性只在分区内成立：不做 key 路由，同一页面连续几次相关上报可能散在不同分区被乱序处理。

## 四、InfluxDB · 时序数据（≈6 分钟）

### 1. 是什么 / 解决什么问题
- 一句话：**专门存"随时间不断产生的一串数值"的数据库**——每分钟 JS 错误量、H5 加载耗时、白屏次数。
- 和业务数据库（MySQL）的本质区别：数据**几乎只写不改**、**批量写入**、查询几乎都是"某个时间范围内的聚合"（平均/最大/求和）——存储结构就为这三点专门优化。
- **与 ES 在本仓的分工（务必讲清）**：**Influx 画「每分钟错误量 / 耗时曲线」；ES 查「这条错误的 stack / 原文」**——admin 看板就是这么拆的。

### 2. 核心概念（3 个）
1. **数据模型：一条数据 = `{ measurement, tags, fields, timestamp }`**。
   - measurement ≈ 表名（本仓例：`fe_error_v2_metrics`、`h5_load_time_metrics`）；
   - **tags** = 用来筛选/分组的标签（如 `app_key`、`time_slice`、`error_type`），**有索引**；
   - **fields** = 真正的数值（如 `count`、`user_count`、`tp95`），**没索引**，是被聚合的对象；
   - timestamp 是一切查询的主轴。
2. **Series 基数**：一个 series = measurement + tags 的唯一组合。它是 InfluxDB 最重要的性能概念——90% 的性能问题源于此（见踩坑）。
3. **保留策略**：本仓封装了 **SHORT / LONG** 两套客户端——细粒度（分钟 / 五分钟 / 小时）走 SHORT（约 3 个月），天 / 月级汇总走 LONG（约 2 年），由 `time_slice` 决定走哪套。时序数据"越新越有价值"，过期自动淘汰，不必手写清理脚本。

### 3. 前端类比
- **类比**：
  - 一条数据点 ≈ 一个带时间戳的 JS 对象；整张表 ≈ 一条 `[{time, ...}, ...]` 的监控数组。
  - **tag vs field ≈ 路由参数（用来定位/筛选）vs 表单数据（承载的内容本身）**——前者建索引、后者不建，和"什么该放 URL 什么该放 body"是同一类判断。
  - Flux 查询语言 ≈ 数组链式调用：`from() |> range() |> filter() |> aggregateWindow()` 读起来就是 `filter().map().reduce()`（或 RxJS 的管道）。
- **类比失效的地方（重点提醒）**：
  - 前端埋点是"采几个点、画条曲线"；时序库面对的是**每秒成千上万点的高频写入**，所以一切设计（批量写、只追加、自动过期）都围绕写入吞吐。
  - 前端没有对应物的概念——**series 基数爆炸**：把 `userId`、`traceId`、甚至未归一化的完整 URL 这种"每个值都不同"的字段放进 tag，series 数量会冲到百万级，索引内存直接爆掉。正确做法是高基数值放 field，tag 只放 `app_key`、`time_slice`、有限枚举的 `error_type` 这类。
  - 查询习惯不同：在 TSDB 里**任何查询都必须带时间范围**，否则等于全表扫描——这是最常见的超时事故来源。

### 4. 典型场景 & 踩坑
- **本仓 measurement 举例**（前端统计点）：
  - `fe_error_v2_metrics`：FE 错误量 / 影响用户数（`feOneMinuteAlarm` 的数据源）
  - `fe_performance_metrics` / `h5_load_time_metrics`：页面性能、H5 加载各阶段耗时
  - `fe_blank_screen_metrics`：白屏次数 / 用户数
  - `fe_page_access_metrics` / `fe_region_error_metrics`：访问量、分地域错误
  - `fe_issue_metrics`：Issue 日汇总（由 `calFeIssueData` 写入）
- **典型 tags**：`app_key`、`time_slice`、`url`、`type` / `sub_type`（如 jsError、timeout）、`stable_sig`——设计统计点时就要想清楚什么能进 tag。
- **场景**：admin 错误趋势图读 Influx；点进某条错误看 stack 读 ES——同一条业务链路的两种读法。
- **踩坑**：
  - 高基数值进 tag → series 爆炸 → 写入/查询全面劣化（设计 FE 统计维度时就要想清楚"什么能当 tag"）。
  - 查询不带时间范围 / 只用 field 条件过滤（不走索引）→ 超时。排查第一步：先缩小时间范围 + 用 tag 过滤。

## 五、收尾：串成一条链路（1–2 分钟）

- **用「前端 JS 错误」把四个模块各就各位**（建议画成流程图讲）：
  1. FE SDK 上报一条 JS 错误 → `server` 写入 **Kafka** Topic `boss.arch.monitor.apm_action`（消息：上报与下游解耦）；
  2. 消费组 `apm.action.es.listener` 写入 **ES** 日索引（如 `apm_action_js_error&action_js_monitor&20260903`）（搜索：留下可检索的明细原文）；
  3. 另一路 compactor 聚合并转发到 `metrics_log` → calculator 写入 **InfluxDB** measurement `fe_error_v2_metrics`（时序：每分钟错误量曲线）；
  4. **xxl-job** 的 `feOneMinuteAlarm` 到点查 Influx 做告警；`preCreateTomorrowEsIndex` / `removeExpiredApmEsData` 负责索引时钟（调度：驱动告警与数据生命周期）；
  5. 你在 **admin** 上看趋势（Influx）再点开详情（ES）——四块基建各就各位。
- **提炼共性**：这四个基础设施都在回答同一类问题——把前端"单进程内存版"的能力（定时器、filter、EventBus、埋点曲线）升级为**多机、持久、容错**的版本。代价是引入三件前端几乎不碰的事：**选一台机器来跑（调度/分区）、可能重复所以必须幂等（at-least-once）、数据有同步延迟（近实时/异步）**。
- **给学习路径**：
  - 想动手：从读一条 FE 上报链路开始——`ActionLogController` → Kafka → `ApmActionToEsListener` / metrics 写入；再看一个 `@XxlJob("feOneMinuteAlarm")`，这两个的"接入体验"最接近前端写接口；
  - 想深入：ES 看按日索引与 DSL 查询；Kafka 看同 Topic 多消费组；时序方向看 `fe_error_v2_metrics` 的 tag 设计与 SHORT/LONG 保留策略；
  - 本仓对照：`TopicConstants`、`InfluxDBMeasurementConstants`、`zhipin-apm-schedule/.../xxljob`、`zhipin-apm-admin` 的 FE 相关 Controller；团队内部资料 `fe-java` 目录下还有各模块深度长文（本分享即其浓缩版 + 本仓落点）。
