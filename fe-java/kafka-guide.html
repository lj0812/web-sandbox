● 写给前端工程师

Kafka 到底是什么？

一句话：Kafka 是一个分布式、持久化的消息系统。如果说你熟悉的 mitt / EventBus 是"进程内、内存里、用完即丢"的事件总线，那 Kafka 就是把这套 发布订阅模型搬到了服务器集群上，还给每条消息上了"永久保险"——写盘、可重放、可以有很多个消费者各自独立消费。

01 · 核心类比

把 Kafka 想象成"跨服务器的 EventBus"

前端 · mitt / EventBus
emitter.emit('order:paid', data)
事件发到内存里，页面刷新/组件销毁后事件历史就没了，只有当前在监听的组件能收到。
≈
Kafka · Producer
producer.send("order-paid", data)
事件被写入磁盘并保留一段时间（比如 7 天），谁都可以在任意时间"回放"这段历史。
前端 · on 监听
emitter.on('order:paid', fn)
同一个事件，多个组件各自 on，互不干扰，谁注册谁收到。
≈
Kafka · Consumer Group
@KafkaListener(topics="order-paid")
不同的"消费者组"（比如短信服务、积分服务）各自独立消费同一份消息，互不影响。

02 · 术语对照表

Kafka 概念 ↔ 前端概念

Kafka 术语前端类比说明
Topic 事件名称 就像 emitter.emit('topic名', ...) 里的事件名，一类消息的分类频道。
Producer emit 的一方 发消息的服务，比如"下单服务"发出 order-paid 事件。
Consumer on 的一方 监听并处理消息的服务，比如"发短信服务"。
Consumer Group 一组订阅者 同组内多个实例分摊消息（类似多个 worker 分工），不同组之间互不影响、都能收到完整消息。
Partition 数组分片 一个 Topic 拆成多个分区并行处理，类似把长列表 chunk 成多份并行渲染/处理，提高吞吐。
Offset 数组下标 / 已读游标 消费者记录"我读到第几条了"，类似分页/无限滚动里的 cursor。
Broker 服务器节点 运行 Kafka 的一台机器，多个 Broker 组成集群（对应"分布式"三个字）。
Message / Record 事件 payload 一条消息，类似 emit 时传的 data 对象，通常是 JSON。

04 · 为什么不直接用接口调用

Kafka 解决的核心问题

解耦
下单服务不需要知道有多少个下游要处理"支付成功"这件事，就像组件 emit 事件时不需要关心谁在 on。新增一个消费方，不用改 Producer 代码。
削峰填谷
秒杀瞬间涌入的十万条消息先落到 Kafka 里排队，后端按自己的处理能力慢慢消费，类似前端的节流/队列，不会被瞬时流量打垮。
可回放
消息持久化在磁盘上，消费者挂了重启后可以从上次的 offset 继续读，甚至重置 offset 重新消费一遍历史消息——这是内存版 EventBus 完全做不到的。
顺序保证（分区内）
同一个分区内消息严格有序，类似数组按下标顺序处理；但跨分区不保证全局顺序，需要按业务 key（如订单号）路由到固定分区来保证同一订单的消息有序。

05 · 在 Java 项目里长什么样

Spring Kafka 的最小示例

对应关系：@KafkaListener 大致相当于前端里的 emitter.on(...)，方法被自动调用； KafkaTemplate.send(...) 相当于 emitter.emit(...)。 

// 发送消息 —— 类似 emitter.emit('order-paid', order)
@Service
public class OrderService {
    private final KafkaTemplate<String, Order> kafkaTemplate;

    public void payOrder(Order order) {
        // topic 名, key(决定进哪个分区), 消息体
        kafkaTemplate.send("order-paid", order.getId(), order);
    }
}

// 消费消息 —— 类似 emitter.on('order-paid', fn)
@Component
public class SmsConsumer {

    @KafkaListener(topics = "order-paid", groupId = "sms-service")
    public void onOrderPaid(Order order) {
        smsClient.send(order.getUserPhone(), "您的订单已支付成功");
    }
}

06 · 容易搞混的地方

Kafka ≠ mitt/Vuex，别踩这几个坑

  • 不是内存态：Vuex/Pinia store 进程重启数据就没了；Kafka 消息默认写盘并按时间/大小保留，重启服务不会丢历史消息。
  • 不是请求-响应模型：它更接近"广播"，Producer 发完就不管了，不像 axios 请求那样等一个返回值。如果需要"结果"，通常是消费者处理完再发一条新消息（比如 order-notified）。
  • 分区 ≠ 随便并行：同一个 key（比如同一个用户 id）的消息会固定进同一个分区，这样才能保证这个用户的消息是有序处理的，别以为分区越多性能越无脑好。
  • Consumer Group 是"组"级别的负载均衡：组内多个实例会分摊分区（类似多个 tab 页共享一份任务队列，各自处理不同的部分），但组与组之间是各自拿到完整的一份数据。
💡
一句话记忆： Kafka 就是一个"带持久化、支持多消费者独立回放、可以水平扩展"的分布式版 EventBus。 理解了这一点，剩下的 Topic / Partition / Offset / Consumer Group 都只是在解决"怎么把这个 EventBus 扩展到多台机器、保证数据不丢、还能并行处理"这几件事而已。
