为什么是这四个放在一起讲

它们不是随机拼盘——每一个都站在后端系统的一个基础位置上。先记住这张骨架图，后面的细节都往这四个格子里放。

后端系统的四个基础位置

后端位置回答的问题基础设施你的前端原型
调度 有些事要「到点自动做」——对账、过期清理、数据同步 xxl-job · 分布式任务调度 setInterval / cron
搜索 有些数据要「按内容找」——商品搜索、日志检索 Elasticsearch · 全文搜索引擎 搜索框 + Array.filter

◇
贯穿全场的一条主线：这四样东西，前端都有「单进程、内存版」的原型。后端基础设施做的事，就是把它们升级成 多机、持久化、出了故障还能活 的版本。所以每个模块你只需要补一件事——升级过程中多出来的那几个概念。

01
调度 · SCHEDULING

xxl-job · 分布式任务调度

分布式环境里的 setInterval + cron——解决"多台机器时，到点的任务由谁来跑、怎么保证只跑一次、跑失败了怎么办"。

≈ 6 min
①是什么 · 解决什么问题≈ 1 min
单机 cron 在多副本部署下会失控：3 个副本都配了同一个定时任务 → 同一件事被执行 3 遍；某台挂了也没人知道。 xxl-job 的答案：把「决定何时跑、谁来跑」和「真正干活」拆成两个独立角色，中间用 MySQL 做共享状态。
②核心概念（只讲 3 个）≈ 1.5 min
概念 1调度中心 / 执行器分离

调度中心 admin：独立 Web 管理台，管任务配置、按 cron 到点触发、选机器、记日志。执行器 Executor：嵌在业务应用里的 SDK，被动接收 HTTP 触发，跑 @XxlJob 方法。

概念 2执行器组 + 心跳

同一应用的多个副本以相同 AppName 注册，自动聚成一个"组"；每 30 秒写一次心跳，90 秒没心跳就被摘除。组是一个「看不见的集群」。

概念 3路由策略

一次触发，从组里选一台执行：轮询 / 随机 / 故障转移……例外是分片广播：每台都收到、各带不同分片号，用于多机并行分摊。

"上一次还没跑完，新触发又来了"——和前端处理在途请求是同一类问题。
⚠ 类比在这里失效 · 别带着错误心智模型走
  • 定时器是单进程、内存态：页面关了就没了，也不存在"谁来跑"的选择。xxl-job 的调度方和执行方是两个进程甚至两台机器，靠 HTTP + MySQL 通信——所以才有注册、心跳、路由这一整套东西。
  • 投递语义不同：setTimeout 错过就错过了；xxl-job 是 at-least-once——重试与补触发意味着任务可能执行不止一次，任务代码必须幂等（对应前端的"按钮防连点"经验，但这层在后端永远省不掉）。
  • "组"是看不见的：谁在跑任务，以 admin 的注册地址为准，而不是你以为部署了哪些实例。
④典型场景 · 高频踩坑≈ 1.5 min
典型场景 每天 0 点对账出报表；优惠券到期批量失效；每 5 分钟把 MySQL 新数据同步到 ES（呼应模块二：搜索的数据从哪来）。
踩坑 · 幽灵执行器（真实事故） 注册只看「能不能连上同一套 admin + MySQL」，不看部署在哪。同事本地跑着旧版本服务也注册进了同一个执行器组，轮询路由下触发在新代码和旧代码之间交替——表现为「配置明明改了，旧行为隔一次出现一次」。 教训：判断"谁在跑任务"的唯一权威来源是 admin 的注册地址列表和调度日志，不是 k8s 的 Pod 列表。
踩坑 · 分片广播 ≠ 天然安全 代码里不读 shardIndex，每台机器就会把全量逻辑各跑一遍——通知发 N 份、数据算 N 遍。广播必须配合分片编码使用。
02
搜索 · SEARCH

Elasticsearch · 全文搜索

MySQL 擅长"按条件精确查一条记录"，ES 擅长"在一堆文本里搜出相关内容，并按相关度排序"——基于倒排索引的分布式搜索引擎。

≈ 6 min
①是什么 · 解决什么问题≈ 1 min
数据库自带的 LIKE '%关键词%' 是"拿关键词去每一行里找"——数据量大了必然全表扫描，更没有中文分词、纠错、相关度排序。 ES 反过来：提前把「每个词出现在哪些文档里」整理成一张表，查询时直接按词查文档。这就是倒排索引——"搜索为什么快"的全部答案。
倒排索引 · 先分词，再按词查文档
原始文档
doc1: "苹果手机 promax 黑色"
doc2: "苹果笔记本电脑"
doc3: "华为手机 promax"
→
倒排索引（写入时就建好）
苹果doc1, doc2
手机doc1, doc3
promaxdoc1, doc3
笔记本doc2

搜"苹果手机"→ 查表直接命中 doc1（两词都命中，分数最高），全程不扫原文。

②核心概念（只讲 3 个）≈ 1.5 min
概念 1倒排索引

写入时就完成分词、建好「词 → 文档列表」。查询成本只和命中的词有关，与总数据量基本无关——这是和 LIKE 的本质区别。

概念 2文档模型

Index ≈ 表，Document ≈ 一行（就是一个 JSON 对象），Mapping ≈ 表结构——核心是定义"每个文本字段怎么分词"，中文场景配 ik 分词器。

概念 3分片 + 副本

一个 Index 拆成多个 Shard 散到不同节点并行处理——水平扩展的关键；Replica 保证节点挂了数据还在，还能分摊查询。

③前端类比≈ 2 min
前端类比 · 先建立熟悉感
前端
Array.filter + sort（带打分）
≈
Elasticsearch
预建索引、分布式的超级过滤器
一句话记忆：ES = 预先建好索引、天生分布式的「超级 Array.filter + 打分排序」。
前端 · 查询写法
match ≈ 搜索框 · term ≈ === · range ≈ >= <= · bool ≈ && || !
≈
ES · Query DSL
用 JSON 写查询条件（REST API 调用）
所有操作都是 HTTP REST——和前端调接口一模一样，只是请求体是 JSON。
⚠ 类比在这里失效 · 别带着错误心智模型走
  • filter 每次全量扫一遍；ES 靠的是写入时预建的倒排索引——成本在写入侧已经付过了。
  • filter 只回答"匹配不匹配"；ES 还给每条结果打相关度分（BM25）并排序——"有多匹配"是前端过滤里没有的维度。
  • 一致性不同：ES 是近实时（写入后约 1 秒才能搜到），且没有事务——所以 ES 永远不当主数据库用：MySQL 是数据源头，ES 只是一份"用来搜索的副本"（这份副本怎么同步过来，正是模块一 / 模块三的活）。
  • text vs keyword 是前端没有的概念：text 会分词（用于全文搜），keyword 不分词（用于精确匹配）——对 text 字段做精确匹配会查不到。
④典型场景 · 高频踩坑≈ 1.5 min
典型场景 电商站内商品搜索——中文分词、拼音纠错、关键词高亮、筛选面板聚合；日志集中检索——ELK（Elasticsearch + Logstash/Filebeat + Kibana）。
踩坑 · Mapping 只能加不能改 字段类型一旦建好无法修改，改类型要重建索引、重新导数据。第一天就要规划好分词方式。
踩坑 · 深度分页 from + size 超过 1 万条性能急剧下降（每个分片都要取 from+size 条再合并排序）。正确姿势是 search_after 游标分页——类似前端无限滚动用 cursor 而不是 offset。
03
消息 · MESSAGING

Kafka · 分布式消息系统

把你熟悉的发布订阅模型搬到服务器集群上，还给每条消息上了"持久保险"——写盘、可重放、多个消费者各自独立消费。

≈ 6 min
①是什么 · 解决什么问题≈ 1 min
三件事：解耦（下单服务不需要知道谁要处理"支付成功"）、削峰（秒杀流量先落盘排队，后端按自己的速度消费）、可回放（消费者挂了重启，从断点继续读）。 如果说 mitt / EventBus 是"进程内、内存里、用完即丢"的事件总线，Kafka 就是它的跨服务器、持久化版本。
②核心概念（只讲 3 个）≈ 1.5 min
概念 1Topic

一类消息的频道，如 order-paid。Producer 往里发，Consumer 从里面读——对应事件名、emit 的一方、on 的一方。

概念 2Partition + Offset

一个 Topic 拆成多个分区并行读写提吞吐，分区内严格有序。Offset 是消费者的"已读游标"——重启后从游标继续。

概念 3Consumer Group

同组内多个实例分摊消息（负载均衡）；不同组之间各自拿到完整一份（广播）。一份消息天然同时服务多个下游业务。

→

⚠ 类比在这里失效 · 本模块重点，逐个说清
  • 持久化：EventBus 是内存态，页面刷新事件历史就没了；Kafka 消息写磁盘、按时间保留（比如 7 天），任何人可在任意时间回放这段历史。
  • 消费者组：前端是"谁 on 谁收到"；Kafka 的"组"引入组内分摊——同组 3 个实例平分分区，像多个 worker 分工。"组"这个负载均衡单位前端完全没有对应物。
  • 分区：前端事件没有"分片并行"。Kafka 靠分区提吞吐，代价是只有分区内有序——要保证同一订单的消息有序，必须用订单号做 key 路由到同一分区。
  • 不是请求-响应：不像 axios 等返回值，Kafka 是"发完就不管"；想要结果，得让消费者处理完再发一条新消息。
④典型场景 · 高频踩坑≈ 1.5 min
典型场景 订单支付成功后，短信服务、积分服务、数据仓库同步三个消费者组各自独立消费——新增一个下游，生产者一行代码都不用改。大促秒杀时兼做削峰缓冲。
踩坑 · 消息会重复 投递语义同样是 at-least-once：网络抖动、消费者重启都可能导致同一条消息被处理两次——消费者必须幂等（和模块一殊途同归：分布式下幂等是硬要求）。
踩坑 · 顺序性只在分区内 不做 key 路由，同一订单的"支付"和"发货"可能散在不同分区被乱序处理。需要顺序的业务，用业务 ID 做消息 key。
04
时序 · TIME-SERIES

InfluxDB · 时序数据库

专门存"随时间不断产生的一串数值"——CPU、QPS、接口耗时。和 ES 互补：时序库看"数值趋势"，ES 看"具体发生了什么"。

≈ 6 min
①是什么 · 解决什么问题≈ 1 min
和业务数据库的本质区别：数据几乎只写不改、批量写入、查询几乎都是"某个时间范围内的聚合"（平均 / 最大 / 求和）。 这三个特点决定了它的一切设计——存储结构就为"高频写入 + 按时间查"专门优化，而不是拿来硬套业务表。
②核心概念（只讲 3 个）≈ 1.5 min
概念 1数据模型四件套

一条数据 = { measurement, tags, fields, timestamp }。tags 是用来筛选/分组的标签（有索引）；fields 是真正的数值（没索引，被聚合的对象）。

概念 2Series 基数

一个 series = measurement + tags 的唯一组合。InfluxDB 最重要的性能概念——90% 的性能问题源于此（见踩坑）。

概念 3保留策略 + 降采样

时序数据"越新越有价值"：旧数据自动聚合降精度、到期自动删——数据生命周期是内建能力，不用写清理脚本。

⚠ 类比在这里失效 · 别带着错误心智模型走
  • 量级不同：前端埋点是"采几个点、画条曲线"；TSDB 面对的是每秒成千上万点的高频写入——所以一切设计围绕写入吞吐（批量、只追加、自动过期）。
  • series 基数爆炸是前端没有对应物的概念：把 userId、traceId 这种"每个值都不同"的字段放进 tag，series 会冲到百万级，索引内存直接爆掉。高基数值放 field，tag 只放 host、region 这种有限枚举。
  • 查询习惯不同：任何查询都必须带时间范围，否则等于全表扫描——这是前端查数组时不存在、在 TSDB 里最常见的超时事故来源。
④典型场景 · 高频踩坑≈ 1.5 min
典型场景 监控大盘：应用把 CPU / QPS / 耗时指标写进 InfluxDB，Grafana 接上画图、配告警；IoT 场景存设备上报的传感器读数。
踩坑 · 高基数值进 tag userId / requestId 当 tag → series 爆炸 → 写入查询全面劣化。设计指标的第一天就要想清楚"什么能当 tag"。
踩坑 · 查询超时 不带时间范围、或只用 field 条件过滤（不走索引）→ 全表扫描超时。排查第一步：缩小时间范围 + 改用 tag 过滤。
收尾 · 1–2 分钟

一条链路，把四个模块各就各位

用一个电商下单链路回顾全场——四个基础设施不是孤立的工具，而是各司其职地长在同一套系统里。

  1. Kafka支付成功，发一条消息出去

    订单服务往 order-paid 发一条消息——消息层负责服务间解耦通信，发完不等回复。

  2. InfluxDB各自消费，指标落库

    短信服务、积分服务作为不同消费者组各自处理；处理耗时、成功率等指标持续写入时序库——系统的"心电图"。

  3. xxl-job定时把数据搬去搜索引擎

    调度中心每 5 分钟触发一次，把 MySQL 里的新订单同步进 ES——调度层是驱动数据流转的"时钟"。

  4. Elasticsearch按内容搜出来

    客服在后台按关键词搜出这笔订单——搜索层负责从海量数据里按内容找东西。四个角色闭环。

带走的三句话

它们都是"前端的升级版"

定时器、filter、EventBus、埋点曲线——前端都有原型；后端基础设施只是把它们变成多机、持久、容错的版本。

为此多了三件新事

选一台机器来跑（调度/分区/路由）、可能重复所以必须幂等（at-least-once）、数据有同步延迟（近实时/异步消费）。

以后遇到新中间件的方法

先问"它解决前端的哪个问题"，再问"为分布式多了哪些概念"——今天的四个模块就是这个方法的四次演练。
