01

表设计与数据类型

类型选错，后面所有优化都是在还债。核心原则：够用就好，别为"可能用得上"预留过大字段。

字段类型选择速查

场景推荐类型说明
主键BIGINT UNSIGNED AUTO_INCREMENT不要用 INT，怕业务量涨起来溢出
金额DECIMAL(12,2)绝不用 FLOAT/DOUBLE，浮点误差在金额场景是事故
状态枚举TINYINT + 代码里维护常量别用 ENUM，改值要改表结构，扩展性差
时间DATETIMETIMESTAMP 有 2038 年上限，且受时区设置影响
短文本VARCHAR(n)n 按实际业务上限给，不要无脑 255
大文本/富文本TEXT频繁读取的大字段建议拆到独立表，避免拖慢主表扫描
是否删除TINYINT(1) deleted配合唯一索引做"软删除"要格外小心，见下文
⚠
NOT NULL 尽量给默认值业务字段能设 NOT NULL DEFAULT xxx 就不要允许 NULL。NULL 参与索引统计、比较、聚合时都有额外心智负担（WHERE col != 1 天然漏掉 NULL 行），前端习惯的"undefined 当空值处理"在这里没有

标准业务表模板

CREATE TABLE `order` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `order_no`    VARCHAR(32)  NOT NULL -- 业务单号，对外展示用，和自增id分开,
  `user_id`     BIGINT UNSIGNED NOT NULL,
  `amount`      DECIMAL(12,2) NOT NULL DEFAULT 0,
  `status`      TINYINT NOT NULL DEFAULT 0 -- 0待支付 1已支付 2已取消,
  `deleted`     TINYINT(1) NOT NULL DEFAULT 0,
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`),
  KEY `idx_user_status` (`user_id`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

类比一下：这张表里的 create_time / update_time / deleted 就像前端埋点里每个对象都会带的 createdAt / updatedAt，是团队约定的通用字段，几乎每张业务表都该有。

02

索引设计

InnoDB 索引底层是 B+树。可以把它类比成 Vue 的响应式依赖收集：建对了索引，查询才能"精准更新"而不是全表遍历。

两种索引，一个概念要分清

聚簇索引（主键索引）

叶子节点存的是整行数据。一张表只有一个。相当于数据本身就是按主键顺序物理排列的。

二级索引（普通索引）

叶子节点存的是"索引列值 + 主键值"。查到之后要拿主键回表查完整行——这就是"回表"的由来。

最左前缀原则

联合索引 (a, b, c) 相当于按 a 排序，a 相同再按 b 排序，以此类推。只有从最左列开始连续使用，索引才生效：

-- 索引 idx_user_status(user_id, status) 有效场景
WHERE user_id = 1                     -- ✅ 用到 user_id
WHERE user_id = 1 AND status = 0       -- ✅ 两列都用到
WHERE user_id = 1 AND status > 0       -- ✅ status 范围查询前的等值仍生效

-- 失效场景
WHERE status = 0                      -- ❌ 跳过了 user_id，索引用不上

覆盖索引：省掉回表

如果 SELECT 的列全部包含在索引里，查询不需要回表，直接在索引树上就能返回结果，性能显著提升：

-- 索引 idx_user_status(user_id, status)
SELECT user_id, status FROM `order` WHERE user_id = 1; -- ✅ 覆盖索引，不回表
SELECT * FROM `order` WHERE user_id = 1;             -- 需要回表取其它列

常见导致索引失效的写法

写法问题
WHERE YEAR(create_time) = 2026对索引列做函数运算，无法走索引，改成范围查询
WHERE phone LIKE '%1234'前置 % 无法走 B+树的有序性，只有 LIKE 'abc%' 这种前缀匹配才有效
WHERE id != 100不等于条件通常放弃索引，走全表扫描
WHERE age = '18'（age 是 int）字符串与数字隐式转换，索引失效，务必保证类型一致
联合索引跳过中间列见上方最左前缀原则
✓
用 EXPLAIN 验证，别靠猜任何"这个索引是否生效"的判断都应该跑一下 EXPLAIN 确认，重点看 type（ref/range 优于 index，远优于 ALL）和 key 列，第 03 节详细展开。
03

SQL 优化

优化的第一步永远是"看懂执行计划"，而不是凭经验瞎猜。

EXPLAIN 关键字段

字段关注点
type访问类型，性能从好到差：const > ref > range > index > ALL。出现 ALL 基本等于全表扫描，要重点排查
key实际用到的索引，为 NULL 说明没走索引
rows预估扫描行数，越小越好
Extra出现 Using filesort（额外排序）、Using temporary（用了临时表）都是优化信号
EXPLAIN SELECT * FROM `order`
WHERE user_id = 1001 AND status = 0
ORDER BY create_time DESC LIMIT 20;

排查慢查询

-- 开启慢查询日志（生产建议配合监控平台，而非直接改配置）
SET GLOBAL slow_query_log = 1;
SET GLOBAL long_query_time = 1; -- 超过1秒记为慢查询

-- 查看当前正在执行的 SQL，定位卡住的连接
SELECT * FROM information_schema.processlist
WHERE time > 5 ORDER BY time DESC;

SELECT * 的代价

类比前端接口设计：SELECT * 就像后端不管前端要什么字段，把整个对象全丢回来——多传的数据浪费带宽，这里则是多占用回表成本、多传输网络流量、还可能因为字段变更悄悄破坏上层代码假设。业务代码里按需 SELECT 具体列。

JOIN 的基本原则

  • 小表驱动大表：MySQL 优化器通常会自动选择，但写法上把过滤条件多的表放前面有助于优化器判断
  • 参与 JOIN 的字段一定要有索引，否则每次关联都是嵌套循环扫描
  • 业务表超过 3～4 张大表 JOIN，考虑是否该在应用层拆成多次查询，用代码里聚合（对前端来说类似"别在一个 GraphQL 查询里塞十层嵌套"）
04

分页与大数据量场景

列表分页几乎是每个后台系统的标配功能，也是最容易随着数据量增长而"温水煮青蛙"变慢的地方。

深分页问题

-- 页码越大越慢：MySQL 要先扫描并丢弃前 100000 条，再取 20 条
SELECT * FROM `order` ORDER BY id LIMIT 100000, 20;
⚠
LIMIT offset, count 的 offset 不是"跳过"，是"先取出再丢弃"offset 越大，扫描的无效行越多，这是深分页变慢的根本原因，不是索引没建对。

解法一：游标分页（推荐用于"下一页"场景，如无限滚动）

-- 记录上一页最后一条的id，直接用条件过滤代替 offset
SELECT * FROM `order`
WHERE id < :last_id
ORDER BY id DESC LIMIT 20;

这跟前端虚拟列表 / 无限滚动的思路一致：不依赖"第几页"，而是依赖"上一个游标在哪"。

解法二：延迟关联（需要跳页场景，如后台管理系统页码输入）

-- 先在索引上定位主键，再用主键回表，避免大量列的深度扫描
SELECT o.* FROM `order` o
INNER JOIN (
  SELECT id FROM `order` ORDER BY id LIMIT 100000, 20
) t ON o.id = t.id;

统计总数（COUNT）的取舍

后台列表经常需要"共 xx 条"，但精确 COUNT(*) 在大表上本身就有成本。常见做法：

  • 业务允许的话，用近似值（如 information_schema.tables 里的 TABLE_ROWS，仅供参考不精确）
  • 前端改成"加载更多"代替"共 N 页"，从产品设计上规避这个问题（很多海外 SaaS 后台就是这么做的）
  • 确实需要精确值，考虑维护一张计数表，插入/删除时同步更新，而不是每次现查

事务与隔离级别

下单、支付、转账这类"多个写操作必须同时成功或同时失败"的场景，都要靠事务兜底。

ACID 用一句话记

特性一句话
原子性 Atomicity事务里的操作要么全成功，要么全回滚，没有中间态
一致性 Consistency事务前后数据都要满足业务约束（比如余额不能为负）
隔离性 Isolation并发事务之间互不干扰，看不到彼此的中间状态
持久性 Durability提交后即使宕机，数据也不会丢

四种隔离级别（MySQL 默认 REPEATABLE READ）

隔离级别脏读不可重复读幻读
READ UNCOMMITTED会发生会发生会发生
READ COMMITTED不会会发生会发生
REPEATABLE READ（默认）不会不会InnoDB 用 MVCC + 间隙锁基本规避
SERIALIZABLE不会不会不会（但退化为串行执行，性能差）
✓
90% 的业务场景用默认级别 REPEATABLE READ 就够不需要手动调整隔离级别，除非有特殊的强一致性要求（比如金融对账场景可能要评估 SERIALIZABLE）。

转账场景标准写法

START TRANSACTION;

UPDATE account SET balance = balance - 100
WHERE id = 1 AND balance >= 100; -- 用条件代替先查后改，防止超卖

-- 检查上一步是否真的影响了1行，影响0行说明余额不足，需要回滚
UPDATE account SET balance = balance + 100
WHERE id = 2;

COMMIT;
-- 任意一步异常：ROLLBACK;
⚠
大事务是性能杀手事务里不要塞进大量非必要逻辑（比如调用第三方接口、发消息、跑循环）。事务越大，占用行锁的时间越长，越容易和其它事务冲突甚至死锁。原则是"事务只包裹真正需要原子性的数据库操作"。

锁与并发场景

秒杀扣库存、防止重复下单，本质都是"多个请求同时改同一行数据"的并发控制问题。

悲观锁：加锁再改（并发不高、强一致场景）

START TRANSACTION;

-- FOR UPDATE 给这行加排他锁，其它事务的同一行更新会被阻塞等待
SELECT stock FROM product WHERE id = 1 FOR UPDATE;

UPDATE product SET stock = stock - 1 WHERE id = 1;

COMMIT;

乐观锁：改的时候才检查（高并发秒杀场景首选）

-- 不加锁，靠条件保证并发安全，失败就重试或提示"手慢了"
UPDATE product SET stock = stock - 1
WHERE id = 1 AND stock > 0;

-- 应用层判断 affected rows，0 说明库存不足或被别人抢先

可以类比前端的乐观更新（optimistic update）：先假设操作会成功直接改，失败了再纠正，而不是每次都先等一个锁。高并发下吞吐量明显更好。

行锁 vs 表锁 vs 间隙锁

类型说明
行锁InnoDB 默认粒度，只锁命中的行，前提是走了索引；没走索引会退化为锁全表
间隙锁 Gap LockREPEATABLE READ 下用于防止幻读，锁的是"值的区间"而非具体行，INSERT 到这个区间会被阻塞
表锁MyISAM 引擎默认，InnoDB 一般只有 ALTER TABLE 这类 DDL 才会触发，业务代码基本不主动用

死锁怎么排查

SHOW ENGINE INNODB STATUS; -- 找 LATEST DETECTED DEADLOCK 部分

死锁最常见的成因是两个事务以不同顺序更新同一批行。业务上的通用解法：约定固定的加锁顺序（比如永远按 id 从小到大更新），能规避大部分死锁。

高频业务 SQL 模式

这些是几乎每个后台系统都会写到的片段，直接抄改字段名即可用。

批量插入（比循环单条 INSERT 快一个量级）

INSERT INTO log (user_id, action, create_time) VALUES
(1, 'login', NOW()),
(2, 'login', NOW()),
(3, 'logout', NOW());

存在则更新，不存在则插入

INSERT INTO user_stat (user_id, view_count) VALUES (1, 1)
ON DUPLICATE KEY UPDATE view_count = view_count + 1;

软删除 + 唯一索引冲突问题

软删除后，被删记录仍占用唯一索引位，重新创建同名/同 code 数据会因唯一约束报错。常见解法是把删除标记也纳入唯一索引：

ALTER TABLE `order`
  DROP INDEX `uk_order_no`,
  ADD UNIQUE KEY `uk_order_no_deleted` (`order_no`, `deleted`);
-- deleted 用 0/软删时间戳区分，而非固定值1，避免多条删除记录仍互相冲突

按时间范围统计（报表类场景）

SELECT
  DATE(create_time) AS day,
  COUNT(*) AS cnt,
  SUM(amount) AS total
FROM `order`
WHERE create_time BETWEEN '2026-08-01' AND '2026-08-31 23:59:59'
GROUP BY DATE(create_time)
ORDER BY day;
⚠
报表类大范围统计不要直接跑在业务库上建议走只读从库，或用定时任务预计算落到汇总表，避免拖慢线上交易查询。

树形/层级数据（部门、分类）

-- 简单场景：parent_id 自关联，代码里递归组装（前端常见的flat转tree）
SELECT id, parent_id, name FROM department WHERE deleted = 0;

-- MySQL 8.0+ 支持递归 CTE，层级较深时更省心
WITH RECURSIVE dept_tree AS (
  SELECT id, parent_id, name FROM department WHERE id = 1
  UNION ALL
  SELECT d.id, d.parent_id, d.name
  FROM department d
  INNER JOIN dept_tree t ON d.parent_id = t.id
)
SELECT * FROM dept_tree;
08

连接池与运维配置

这部分是"Java 后端特有但前端很少接触"的内容，类比一下会更好理解。

为什么要连接池

每次新建数据库连接都有三次握手 + 认证的开销。连接池（HikariCP 是 Spring Boot 默认）预先建好一批连接复用， 跟前端 axios 复用 HTTP keep-alive 连接、或者浏览器限制同域并发连接数是类似的思路——建立连接是贵操作，能复用就不要重建。

Spring Boot + HikariCP 常用配置

# application.yml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20      # 最大连接数，不是越大越好，受数据库最大连接数限制
      minimum-idle: 5            # 最小空闲连接，避免流量突增时来不及建连接
      connection-timeout: 3000   # 拿不到连接时最多等多久（ms）
      idle-timeout: 600000       # 空闲连接多久后被回收
      max-lifetime: 1800000      # 连接最大存活时间，避免踩到数据库侧的连接超时
⚠
连接池不是越大越快连接数超过数据库能高效处理的并发线程数后，只会增加上下文切换开销，性能反而下降。经验值一般是 CPU 核心数的 2～4 倍，需结合压测调整。

读写分离的基本思路

写操作走主库，读操作走从库，通过 binlog 异步复制同步数据。业务上要接受"主从延迟"，即写入后立刻读可能读到旧数据——这跟前端"乐观更新后接口还没落库，页面已经先展示新状态"是相反方向的同一类问题，都需要在业务层做取舍。

字符集与排序规则

统一使用 utf8mb4（不是 utf8，MySQL 的 utf8 最多 3 字节，装不下 emoji 等 4 字节字符），排序规则推荐 utf8mb4_0900_ai_ci（8.0 默认）或 utf8mb4_general_ci。

常见坑位清单

这些是排查线上问题时反复出现的高频原因，出问题先对着这张表过一遍。

高频大事务导致锁等待超时

事务里塞了循环调用、远程接口，行锁持有时间过长，导致其它请求 Lock wait timeout exceeded。原则：事务只包住数据库操作本身。

高频先查询后更新的竞态条件

"先 SELECT 判断库存，再 UPDATE 扣减"这种写法在并发下会超卖。改成 UPDATE ... WHERE stock > 0 用数据库保证原子性。

中频索引建太多，拖慢写入

每多一个索引，INSERT/UPDATE 都要多维护一棵 B+树。索引不是越多越好，按实际查询模式建，定期清理没用到的索引。

中频忘记给外键关联字段建索引

MySQL 不会自动为 JOIN 用到的列建索引（外键约束本身除外），手动建的关联字段容易漏掉，导致 JOIN 全表扫描。

中频N+1 查询

循环里对每条主记录再单独查一次关联表，等价于前端在 .map() 里对每一项都发一次请求。改成一次 IN 查询或 JOIN，在应用层聚合。

低频但致命忘记 WHERE 条件的批量 UPDATE/DELETE

生产环境务必先跑对应的 SELECT 确认影响范围，重要操作加事务并保留回滚方案，能加 LIMIT 的批量操作尽量加。
