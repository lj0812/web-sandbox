● Elasticsearch

ES 到底是什么？

ES（Elasticsearch）是一个基于 Lucene 的分布式全文搜索引擎，同时也常被当成一种 文档型数据库来用。如果 MySQL 擅长"按索引精确查一条记录"，ES 擅长的是 "在一堆文本里搜出相关的内容，并按相关度排序"——本质是一个预先建好索引、能水平扩展的 "超级 Array.filter + 打分排序"。

01 · 核心概念对照

ES 术语 ↔ 关系型数据库

Elasticsearch关系型数据库类比说明
Index 数据库 / 表 一类文档的集合，比如 products 索引存所有商品。
Document 一行数据 本质是一个 JSON 对象，比如一件商品的完整信息。
Field 列 文档里的一个字段，比如 title、price。
Mapping 表结构 / Schema 定义每个字段的类型，尤其是文本字段"怎么分词"，直接决定搜索效果。
Shard 分表 一个 Index 被拆成多个分片，分布到不同节点并行处理，是 ES 能扩展的关键。
Replica 副本 每个分片的备份，节点挂了也不丢数据，同时能分摊查询压力。

02 · 为什么搜索这么快

核心原理：倒排索引

普通数据库的 LIKE '%关键词%' 是"拿关键词去每一行里找"，数据量大了必然全表扫描很慢。 ES 反过来，提前把"每个词出现在哪些文档里"整理成一张表，查询时直接按词查文档 —— 这就是"倒排索引"。

原始文档
doc1: "苹果手机 promax 黑色"
doc2: "苹果笔记本电脑"
doc3: "华为手机 promax"
→
倒排索引（分词后）
苹果doc1, doc2
手机doc1, doc3
promaxdoc1, doc3
笔记本doc2

搜"苹果手机"时，直接查倒排索引拿到 doc1（两个词都命中，分数最高），不需要扫描原始文档全文。

03 · 为什么不直接用数据库自带的模糊搜索

全文检索能力
支持中文分词、同义词、拼音搜索、拼写纠错、高亮显示，这些 LIKE 完全做不到。
相关度排序
内置 BM25 算法，搜索结果按"匹配程度"打分排序，而不只是"有没有匹配上"。
聚合分析
除了搜索，还能做类似 GROUP BY + 统计的聚合，常用来做日志分析、监控大盘。
水平扩展
天生分布式架构，数据量大了加节点就行，不需要像单机数据库那样做复杂分库分表。

分片 + 副本怎么分布

深色块是主分片（Primary Shard），浅色块是副本（Replica）—— 副本永远和自己的主分片放在不同节点，任意一台机器挂了数据都还在。

05 · 典型使用场景

  • 站内搜索：电商商品搜索、内容站文章搜索，几乎是标配选型。
  • 日志分析（ELK / EFK）：Elasticsearch + Logstash/Filebeat + Kibana，把各服务日志集中存储、检索、可视化。
  • 可观测性里的日志与 Trace 检索：和之前聊的 Prometheus/InfluxDB 是互补关系——指标库看"数值趋势"，ES 看"具体发生了什么"。
  • 推荐 / 风控等场景的复杂条件查询：多字段组合过滤 + 打分，比关系型数据库拼一堆 WHERE 更灵活。

06 · CRUD 操作（REST API）

文档的增删改查

ES 所有操作都通过 HTTP REST 接口完成，和前端调接口一模一样，只不过请求体是 JSON。

操作HTTP 方法示例路径说明
创建索引PUT/products相当于建表
新增文档POST/products/_doc自动生成 ID；用 PUT /products/_doc/1 可指定 ID
查询文档GET/products/_doc/1按 ID 精确获取
搜索POST/products/_search用 DSL 做全文搜索
更新文档POST/products/_update/1部分更新，只传要改的字段
删除文档DELETE/products/_doc/1按 ID 删除
批量操作POST/_bulk一次请求完成多个增删改操作
 
// 新增一条文档
POST /products/_doc
{
  "title": "苹果 iPhone 15 Pro Max 256G 黑色",
  "price": 9999,
  "brand": "Apple",
  "tags": ["手机", "5G", "旗舰"]
}

// 部分更新（只改价格）
POST /products/_update/1
{
  "doc": { "price": 8999 }
}

// 批量操作 —— _bulk 每两行一组（操作 + 数据）
POST /_bulk
{ "index": { "_index": "products", "_id": "2" } }
{ "title": "华为 Mate 60 Pro", "price": 6999 }
{ "delete": { "_index": "products", "_id": "3" } }

07 · Mapping 与分词器

定义字段类型 = 决定搜索效果

Mapping 就像表的 Schema，最关键的是告诉 ES "这个字段要不要分词、用什么分词器"。

text 类型
会被分词，适合全文搜索。如商品标题、文章内容。搜索时也会对查询词分词再匹配。
keyword 类型
不分词，整个值作为一个 token。适合精确匹配：品牌、状态、枚举值、ID。
数值/日期类型
integer、long、double、date 等，支持范围过滤和聚合统计。
nested / object
嵌套对象。object 会扁平化，nested 保持数组内对象的独立性。
// 创建索引时定义 Mapping
PUT /products
{
  "mappings": {
    "properties": {
      "title":    { "type": "text", "analyzer": "ik_max_word" },
      "brand":    { "type": "keyword" },
      "price":    { "type": "double" },
      "createAt": { "type": "date", "format": "yyyy-MM-dd HH:mm:ss" },
      "tags":     { "type": "keyword" }
    }
  }
}
⚠️
注意：Mapping 一旦创建，已有字段的类型不能修改（类似 MySQL ALTER 改字段类型有风险）。 如果要改，需要创建新索引 → 重新导入数据（reindex）。所以一开始就要规划好。

分词器工作流程

一个分词器（Analyzer）= 字符过滤器 → 分词器 → 词条过滤器，三步流水线。

分词器适用场景示例输入 → 输出
standard英文默认，按空格/标点切分"Quick Fox" → [quick, fox]
ik_smart中文智能分词，尽量少切"苹果手机" → [苹果手机]
ik_max_word中文最细粒度，尽量多切"苹果手机" → [苹果, 手机, 苹果手机]
pinyin拼音搜索（插件）"苹果" → [ping, guo, pg]
 
// 测试某个分词器的效果（开发时很常用）
POST /_analyze
{
  "analyzer": "ik_max_word",
  "text": "苹果iPhone15手机很好用"
}
// 输出 tokens: [苹果, iphone15, iphone, 15, 手机, 很好, 好用]

08 · Query DSL —— 搜索的核心语言

ES 的"SQL"，全是 JSON

DSL（Domain Specific Language）是 ES 的查询语言。把它想象成用 JSON 写 SQL —— 所有搜索条件、过滤、排序、分页都通过一个 JSON body 描述。

整体结构一览

POST /products/_search
{
  "query": { ... },       // 搜索条件（核心）
  "sort": [ ... ],        // 排序规则
  "from": 0,              // 分页偏移（类似 OFFSET）
  "size": 10,             // 每页条数（类似 LIMIT）
  "_source": ["title", "price"],  // 只返回哪些字段（类似 SELECT）
  "highlight": { ... },   // 搜索关键词高亮
  "aggs": { ... }         // 聚合统计（类似 GROUP BY）
}

query 里的查询类型

可以类比前端 Array.filter 里写不同的判断条件。

查询类型用途类比
match全文搜索，先分词再匹配搜索框输入关键词
match_phrase短语搜索，词序和位置都要匹配精确短语搜索
multi_match多字段搜索同一关键词同时搜标题、描述
term精确匹配（不分词）=== 判断
terms多值精确匹配IN (...)
range范围过滤BETWEEN、>= <=
bool组合多个条件AND / OR / NOT
exists字段是否存在IS NOT NULL
wildcard通配符匹配LIKE 'app%'
fuzzy模糊/纠错搜索用户拼错了也能搜到

match —— 最常用的全文搜索

// 搜 "苹果手机" → 分词成 [苹果, 手机]，命中任一词即返回
POST /products/_search
{
  "query": {
    "match": {
      "title": "苹果手机"
    }
  }
}

// 要求所有词都命中（AND 逻辑）
POST /products/_search
{
  "query": {
    "match": {
      "title": {
        "query": "苹果手机",
        "operator": "and"
      }
    }
  }
}

term —— 精确匹配（不走分词）

// 精确匹配品牌（keyword 字段用 term）
POST /products/_search
{
  "query": {
    "term": {
      "brand": "Apple"
    }
  }
}

// terms：匹配多个值（IN 查询）
POST /products/_search
{
  "query": {
    "terms": {
      "brand": ["Apple", "Huawei", "Xiaomi"]
    }
  }
}

range —— 范围过滤

// 价格在 3000~8000 之间
POST /products/_search
{
  "query": {
    "range": {
      "price": {
        "gte": 3000,
        "lte": 8000
      }
    }
  }
}

// 日期范围：最近7天的数据
POST /logs/_search
{
  "query": {
    "range": {
      "timestamp": {
        "gte": "now-7d/d",
        "lte": "now"
      }
    }
  }
}

bool —— 组合查询（最重要）

bool 查询相当于 SQL 的 WHERE ... AND ... OR ... NOT ...，是实际业务中用得最多的。

子句含义类比
must必须匹配，参与打分AND
filter必须匹配，不打分（更快）WHERE 过滤
should满足则加分（至少匹配一个）OR（加分项）
must_not必须不匹配NOT / !=
 
// 实际业务示例：搜索"手机"、品牌必须是 Apple、价格 5000-10000、排除二手
POST /products/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "手机" } }
      ],
      "filter": [
        { "term": { "brand": "Apple" } },
        { "range": { "price": { "gte": 5000, "lte": 10000 } } }
      ],
      "must_not": [
        { "term": { "condition": "used" } }
      ],
      "should": [
        { "term": { "tags": "旗舰" } }
      ]
    }
  }
}
💡
filter vs must：filter 不计算相关度分数，ES 可以缓存 filter 结果。 原则：需要影响排序的条件放 must，纯过滤条件（精确匹配、范围）放 filter，性能更好。

multi_match —— 多字段搜索

// 同一关键词同时搜标题和描述，标题权重更高
POST /products/_search
{
  "query": {
    "multi_match": {
      "query": "苹果手机",
      "fields": ["title^3", "description"]
    }
  }
}
// title^3 表示标题字段权重是描述的 3 倍

排序 + 分页 + 高亮

POST /products/_search
{
  "query": { "match": { "title": "手机" } },
  "sort": [
    { "price": "asc" },
    "_score"
  ],
  "from": 0,
  "size": 20,
  "highlight": {
    "fields": {
      "title": {
        "pre_tags": ["<em class='hl'>"],
        "post_tags": ["</em>"]
      }
    }
  }
}
// 返回的 highlight.title 会像这样：["苹果<em class='hl'>手机</em> ProMax"]

09 · 聚合分析（Aggregation）

ES 里的 GROUP BY + 统计函数

聚合可以在搜索的同时统计数据，常用于搜索页面的筛选面板（"品牌分布"、"价格区间"）和数据看板。

聚合类型用途SQL 类比
terms按字段分组（桶聚合）GROUP BY brand
histogram按区间分桶价格每 1000 分一组
date_histogram按时间区间分桶按天/小时统计
avg / sum / min / max指标聚合AVG(price)
cardinality去重计数COUNT(DISTINCT ...)
top_hits每组取 Top N 条文档每组取代表数据
 
// 电商场景：搜"手机"的同时，统计品牌分布和平均价格
POST /products/_search
{
  "query": { "match": { "title": "手机" } },
  "size": 0,  // 不需要文档，只要聚合结果
  "aggs": {
    "brand_distribution": {
      "terms": { "field": "brand", "size": 10 }
    },
    "avg_price": {
      "avg": { "field": "price" }
    },
    "price_ranges": {
      "histogram": { "field": "price", "interval": 2000 }
    }
  }
}
// 返回结果类似：
// brand_distribution.buckets: [{key:"Apple",doc_count:42}, {key:"Huawei",doc_count:38}, ...]
// avg_price.value: 5680.5
// price_ranges.buckets: [{key:2000,doc_count:15}, {key:4000,doc_count:28}, ...]
// 嵌套聚合：每个品牌下的平均价格
POST /products/_search
{
  "size": 0,
  "aggs": {
    "by_brand": {
      "terms": { "field": "brand" },
      "aggs": {
        "avg_price": { "avg": { "field": "price" } }
      }
    }
  }
}

10 · 数据同步方案

MySQL → ES 怎么同步

ES 通常不是数据的"源头"，而是从 MySQL 同步一份过来做搜索。常见同步方式：

方案原理优缺点
同步双写 写 MySQL 的同时写 ES 简单；但有一致性风险，ES 写失败怎么办
异步消息 写 MySQL 后发 MQ 消息，消费者写 ES 解耦，可重试；有短暂延迟
Canal / Debezium 监听 MySQL Binlog 变更，实时同步到 ES 对业务代码零侵入；需要运维中间件
定时全量/增量 定时任务扫描变更数据同步 最简单；延迟大，适合对实时性要求低的场景
💡
实际选择：中小项目用"异步消息"（比如写 MySQL 后发 Kafka/RabbitMQ）就够了； 大厂一般用 Canal 监听 Binlog，对业务完全无侵入。

11 · 性能优化要点

让 ES 跑得更快的关键手段

filter 代替 must
不需要打分的条件一律用 filter，ES 会缓存 filter 结果，重复查询直接命中缓存。
合理设置分片数
每个分片建议 10-50GB。分片太多 = 小文件太多，协调开销大；分片太少 = 无法并行。
避免深度分页
from + size 超过 10000 条性能急剧下降，应该用 search_after 或 scroll API。
keyword vs text
不需要全文搜索的字段（如 ID、状态码）设成 keyword，不走分词，更快更省存储。
_source 按需返回
只 _source: ["title","price"] 返回需要的字段，减少网络传输和序列化开销。
批量写入
用 _bulk API 批量写入，而不是逐条 index。合理设置 refresh_interval（默认 1s）。
// search_after：深度分页的正确方式（游标分页）
POST /products/_search
{
  "query": { "match_all": {} },
  "sort": [{ "price": "asc" }, { "_id": "asc" }],
  "size": 20,
  "search_after": [4999, "abc123"]  // 上一页最后一条的 sort 值
}

12 · 在 Java 项目里怎么接

Spring Data Elasticsearch

Spring 生态里可以用 Spring Data Elasticsearch，写法和 Spring Data JPA 很像；也可以直接用官方 Java Client，用 JSON 拼查询 DSL 更灵活。

// 定义文档 —— 类似前端定义一个 TS interface
@Document(indexName = "products")
public class Product {
    @Id
    private String id;

    @Field(type = FieldType.Text, analyzer = "ik_max_word")
    private String title;   // 用中文分词器

    @Field(type = FieldType.Double)
    private Double price;

    @Field(type = FieldType.Keyword)
    private String brand;
}

// Repository —— 方法名约定即查询
public interface ProductRepository extends ElasticsearchRepository<Product, String> {
    List<Product> findByTitleContaining(String keyword);
    List<Product> findByBrandAndPriceBetween(String brand, Double min, Double max);
}

用 Java Client 写 DSL

// 等价于手写 bool + match + filter 的 DSL
SearchResponse<Product> response = client.search(s -> s
    .index("products")
    .query(q -> q
        .bool(b -> b
            .must(m -> m.match(t -> t.field("title").query("手机")))
            .filter(f -> f.term(t -> t.field("brand").value("Apple")))
            .filter(f -> f.range(r -> r.field("price").gte(JsonData.of(5000)).lte(JsonData.of(10000))))
        )
    )
    .sort(so -> so.field(f -> f.field("price").order(SortOrder.Asc)))
    .from(0).size(20),
    Product.class
);

13 · ES vs MySQL —— 选型对比

对比维度MySQLElasticsearch
擅长事务、精确查询、关联查询全文搜索、模糊匹配、聚合分析
一致性强一致（ACID 事务）近实时（NRT），写入后 ~1s 可搜到
写入单条写入快，支持事务回滚批量写入快，不支持事务
关联查询JOIN 随意写不擅长 JOIN，需提前宽表化（反范式）
数据量单表千万级后需要分库分表天生分布式，TB 级别轻松扩展
排序按索引列排序快按相关度打分排序是强项
💡
实际项目中的经典组合：MySQL 作为数据源（Source of Truth），保证事务和数据完整性； ES 作为搜索引擎，处理全文检索、复杂筛选和聚合统计。两者通过消息队列或 Binlog 同步保持数据一致。

14 · 常见踩坑与注意事项

  • text 字段不能用 term 查询：text 字段存储时已分词，用 term 精确匹配整个值会查不到。要精确匹配请用 .keyword 子字段或设为 keyword 类型。
  • Mapping 不能改只能加：已创建的字段类型无法修改，只能新增字段。要改类型得重建索引 + reindex。
  • 深度分页性能问题：from: 10000, size: 20 意味着 ES 要在每个分片上取 10020 条再合并排序，非常耗内存。超过 10000 条用 search_after。
  • 不要当主数据库用：ES 没有事务，不保证强一致性，硬删除后无法回滚。关键业务数据一定存在 MySQL，ES 只做搜索副本。
  • refresh_interval：默认 1 秒刷新一次，写入后不是立刻能搜到。高频写入场景可以临时调大或关闭 refresh，写完再改回来。
  • 动态 Mapping 的坑：如果不提前定义 Mapping，ES 会自动推断类型。数字字符串可能被推断为 long，后续插入真正的字符串会报错。建议显式定义关键字段。
💡
一句话记忆：ES 就是"预先建好倒排索引、天生分布式的全文搜索引擎"。 数据库解决"精确存取"，ES 解决"从大量文本里搜出相关内容并排序"，两者通常是配合使用而不是互相替代—— 业务数据存 MySQL，需要搜索的字段再同步一份到 ES。
