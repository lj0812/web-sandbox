XXL-JOB
运行机制详解

理解 xxl-job 只需要先接受一条心智模型：调度和执行是分离的两个平面。 调度中心按 cron 只发令一次，执行器是「被选中的那一个」—— 注册进同一个执行器组的进程（无论几个、在哪），都是在竞争这一次派发。

Architecture

架构解剖：控制面与执行面

xxl-job 是「调度中心 + 执行器」两层架构，中间用 MySQL 做共享状态。这个拆分是整个系统一切行为的前提： 谁来决定「何时跑」和「谁来跑」，与真正干活的进程，是两套东西。

xxl-job-admin调度中心

一个独立的 Spring Boot Web 应用。负责：任务的增删改查、cron 解析、到点触发、路由选机、失败重试与告警、调度日志。自身无状态，状态全在 MySQL。

Executor执行器

以 SDK 形式嵌入业务应用（一个 XxlJobSpringExecutor Bean）。启动时自带一个 HTTP server（默认端口 9999），被动接收调度中心的触发请求并执行 JobHandler。

MySQL共享状态

存任务定义（xxl_job_info）、执行器注册表（xxl_job_registry）、调度与执行日志、分布式锁（xxl_job_lock）。是集群之间唯一的「事实来源」。

前端类比 就像 CI/CD：admin 是 GitHub Actions 的控制台与调度服务，执行器是你挂在机房里的 self-hosted runner——平台决定哪个 runner 接单，runner 只管干活并回报结果。你的业务应用 = runner 所在的机器。

两者之间的通信是短连接 HTTP，方向有两条：

  • admin → 执行器：触发请求（携带 jobId、任务参数、分片序号等），打到执行器内嵌 server 的 /run 接口。
  • 执行器 → admin：执行结果回调（成功/失败、耗时），由执行器内的回调线程批量上报，失败会本地暂存并重试。
Registry

注册与心跳：谁有资格接单

执行器不需要手工配置地址。启动后，执行器内置的注册线程每 30 秒向 MySQL 的 xxl_job_registry 表写一次「我还活着」（按 AppName + IP:Port 维度）。 调度中心侧有一个监控线程，把 90 秒没更新心跳的记录直接删除。 任务配置里选「自动注册」时，路由可用的机器列表就是这张表的实时快照。

关键推论 · 幽灵执行器 注册只看「能不能连上同一个 admin + 同一套 MySQL」，不看进程部署在哪。 一台开发机、一个本地起的老版本服务、一台忘了下线的旧主机——只要连上了，它就合法进入路由列表参与接单， 且 k8s 里根本看不到它。心跳停 90 秒才消失。这就是「代码是对的，行为见鬼」这类事故的经典来源。
前端类比 等价于服务注册中心的心跳机制（Nacos / Eureka）：实例上线注册、周期续约、超时摘除。 也像 WebSocket 的 keep-alive——连接在不在，靠心跳说了算，不靠你这边的「设备列表」页面。
Trigger Pipeline

触发链路：一次调度引发的完整旅程

从秒针跳到整点，到业务代码真正执行，中间经过下面这条链。这是理解「为什么只发一份通知」的核心。

  1. 抢锁 · 全局唯一调度权

    调度中心的调度线程每秒醒来一次，先对 xxl_job_lock 行锁做 SELECT ... FOR UPDATE。集群多个 admin 实例同时抢，只有一个抢到——这保证同一时刻全集群只有一套调度逻辑在跑。

  2. 预读 · 未来 5 秒的到期任务

    抢到锁的实例扫描 xxl_job_info，把「下次触发时间 ≤ 当前 + 5s」的任务捞出并立即推进它们的下次触发时间（落库），然后释放锁。预读窗口让调度精度不受单次扫表耗时影响。

  3. 入时间环 · 按秒挂起

    任务被挂到一个 0–59 格的「时间环」（环形缓冲）上，格子的下标就是触发秒。另一个环线程逐秒消费当前格——相当于把「未来 5 秒」摊平成逐秒派发。

  4. 路由 · 选出一台执行器

    按任务配置的路由策略，从该执行器组的注册地址列表里选出目标地址（详见下一节）。非广播策略下，这一步只产出一个地址。

  5. 触发 · 线程池投递

    触发请求进入触发线程池，以 HTTP 打向执行器。线程池分快慢两条：近 10 秒平均触发耗时超 500ms 的任务被隔离进慢池，防止慢任务把触发线程占满、拖垮其他任务的准点率。

  6. 执行 · 每任务一条专属线程

    执行器收到请求后，把任务丢进该 jobId 专属的 JobThread（一线程一任务 + 阻塞队列），运行你的 @XxlJob 方法。执行日志同步写入执行器本地磁盘（logpath/日期/jobId.log），admin 页面看日志其实是反向调用执行器的日志查询接口。

  7. 回调 · 结果归集

    执行结果由回调线程批量推回 admin，写入调度日志。回调失败会本地暂存不断重试，所以 admin 端看到的成功/失败是最终一致的。

前端类比 时间环很像浏览器的事件循环：每一帧（每一秒）只处理「这一帧到期」的任务队列； 预读 5 秒相当于提前把下一批 setTimeout 的回调登记好，避免主线程抖动导致整批迟到。 快慢线程池隔离则等价于前端把「长任务」丢进单独的 Worker，别堵住渲染主线程。

错过触发（Misfire）会怎样

如果 admin 宕机或锁被长时间占用，任务错过了预定触发时间：恢复后调度线程会发现「下次触发时间已过期」， 立即补触发一次（只补一次，不是把错过的每次补齐），然后恢复正常节奏。 所以 admin 短暂不可用后的第一分钟，任务可能晚几秒到——业务代码应按「可能迟到、但不会凭空多跑」来设计。

Routing Strategy

路由策略：多台机器时谁来跑

执行器组里有多台机器时，路由策略决定每次触发挑哪一台。可以完全按负载均衡的术语理解—— 这些名字和 Nginx upstream 的算法几乎一一对应。

顺序类 · 确定性选择
FIRST第一个

固定选列表第一台。列表按注册顺序，实际约等于「最早注册的那台」。

LAST最后一个

固定选列表最后一台，与 FIRST 相反。

负载类 · 打散流量
ROUND轮询

依次轮流。多台机器时最常见的策略——每次触发仍只有一台执行，只是执行者在机器间交替。

RANDOM随机

每次随机一台，长期看近似均匀。

CONSISTENT_HASH一致性HASH

按 jobId 做一致性哈希，同一任务固定落在同一台（机器增减时只迁移少量任务），利于命中本地缓存。

LFU / LRU最不经常 / 最近最久

分别挑「调用频次最低」和「最久没被调用」的机器，追求长期均匀。

健康类 · 派发前先探活
FAILOVER故障转移

按顺序逐台发心跳探测，选第一台存活的。等价于带健康检查的负载均衡。

BUSYOVER忙碌转移

逐台探测且检查对方是否空闲（有无执行中线程），选第一台「活着且空闲」的。

全体类 · 每台都收到
SHARDING_BROADCAST分片广播

触发组内所有机器，每台携带不同的 shardIndex 与共同的 shardTotal。这是让多机「并行分摊」的唯一正规姿势。

高发事故点 · 分片广播 ≠ 天然安全 分片广播会把触发发给每台机器，是否重复执行取决于你的代码是否消费分片参数。 如果 JobHandler 里从不读 shardIndex，那每台机器都会完整跑一遍全量逻辑—— 效果等于「广播重复执行」：通知发 N 份、数据算 N 遍。广播类策略必须配合分片编码使用。 
// 分片广播的正确打开方式：每台只处理自己那片
@XxlJob("demoShardingJob")
public void demoShardingJob() {
    int shardIndex = XxlJobHelper.getShardIndex();  // 本机分片序号
    int shardTotal = XxlJobHelper.getShardTotal();  // 分片总数 = 机器数
    for (Item item : allItems) {
        if (item.getId() % shardTotal == shardIndex) {  // 取模分片
            handle(item);
        }
    }
}
前端类比 分片广播就像把一个数组手动切片分给多个 Worker：arr.filter((_, i) => i % N === myIndex)。 每个 Worker 都拿到完整数组（触发到达所有人），但只处理下标属于自己的那份； 忘了写过滤条件，就是 N 个 Worker 把整个数组各算一遍。
Execution & Fault Tolerance

执行与容错：任务跑起来之后

阻塞策略：上一次还没跑完，下一次又来了

任务执行时间超过调度间隔时（比如每分钟调度、但一次要跑 3 分钟），新触发到达时旧任务仍在执行。阻塞策略决定怎么处理排队的新触发：

策略行为前端类比
SERIAL_EXECUTION
串行排队		新触发进入该任务的阻塞队列，等前一次结束后依次执行。并发数为 1 的请求队列，FIFO 消化。
DISCARD_LATER
丢弃后续		有任务在执行，就直接丢弃本次触发。SWR / React Query 的请求去重：同样的请求在途就忽略新的。
COVER_EARLY
覆盖之前		中断正在执行的旧任务，立即执行新触发。AbortController.abort() 掉旧请求，发出新请求。

失败与超时

  • 失败重试：任务可配置重试次数，触发失败（执行器不可达、执行返回失败）时由调度中心重新派发。
  • 任务超时：配置超时时间后，超时会被调度中心主动 kill（中断执行线程）。
  • 失败告警：失败会向任务配置的告警邮件发送通知。
语义底线 · 至少一次投递 重试、misfire 补触发、回调重发加在一起，xxl-job 的投递语义是 at-least-once： 同一次业务触发，代码有可能被执行不止一次。任务必须幂等—— 发通知前查去重表、写数据用唯一键、状态机先查后改。
前端类比 和前端处理「按钮连点」是同一个问题：网络慢时用户双击提交，服务端可能收到两次请求。 前端的解法（防抖、提交中禁用按钮、服务端幂等键）里，只有「幂等」这一层在分布式调度下永远无法省略—— 也类似 React StrictMode 会故意双调用 effect，你的清理逻辑必须经得起重复执行。
Multi-Pod Deployment

多 Pod 部署：集群下的两种「多」

「多 Pod」要拆成两个独立问题：调度中心多副本怎么办，执行器多副本怎么办。答案完全不同。

调度中心集群：多副本，但调度权只有一个

admin 可以部署多副本做高可用。每个副本的调度线程每秒都在抢 xxl_job_lock 行锁， 同一时刻只有持锁实例在调度；持锁实例挂了，锁在事务超时后释放，其他副本秒级接管。 所以 admin 集群不会导致任务被触发多次——数据库锁是最终仲裁者。

执行器集群：同一 AppName 自动聚合，路由负责分活

业务应用多副本部署时，每个 Pod 里的执行器都以相同 AppName 注册，自动聚成一个执行器组。 此后每次触发按路由策略选一台——这层天然就是水平扩展：Pod 越多，任务被摊得越薄。 需要全量并行时用分片广播 + 分片编码（见上节）。

真实事故复盘 · 本地进程混入路由 现象：数据库渠道配置已改为仅 BossHi，QA 的 Pod 日志也证实只发了 BossHi，但邮件照旧收到。
根因：同事在本地跑着旧版本 schedule 服务，同样注册进了 QA 的 xxl-job。 轮询路由下触发在「QA Pod（新代码）」和「本地机器（旧代码）」之间交替—— 轮到旧代码时按老逻辑邮件 + BossHi 双发。
教训：执行器组是一个「看不见的集群」，k8s 的 Pod 列表不是它的完整成员名单。 判断「谁在跑任务」的唯一权威来源，是 admin 里该执行器组的注册地址列表与调度日志中的触发地址。
前端类比 执行器组类似一个 Service Worker 的「作用域」：你以为只有线上那份脚本在生效， 但如果有人往同一个 scope 注册了另一份（本地代理、旧版本缓存），请求就会被两者随机接管。 排查方式也一样——别看你「以为」注册了什么，去看浏览器（这里是 admin）里实际注册了什么。
Practice

最佳实践清单

  • 任务幂等是硬要求：at-least-once 语义下，重试与补触发都可能让代码多跑一次；通知类任务加去重键。
  • 环境彻底隔离：QA / 预发 / 生产使用各自独立的 admin、MySQL 与执行器 AppName（或至少不同的 accessToken）；本地开发不连共享环境的调度中心。
  • 开启通信鉴权：配置 accessToken，拒绝裸跑的执行器端口。
  • Bean 模式优先：用 @XxlJob 注解管理任务代码，随应用版本发布；慎用 GLUE 线上编辑模式（代码脱离版本控制）。
  • 广播必配分片：使用分片广播的任务，代码必须消费 shardIndex / shardTotal，否则每台机器重复全量执行。
  • 阻塞策略按任务性质选：可丢弃的统计类任务用「丢弃后续」；必须每轮都算的用「串行排队」；只关心最新一轮的用「覆盖之前」。
  • 执行器端口规划：默认 9999，同机多执行器实例必须显式配置不同端口。
  • 排查「谁在跑」三件套：执行器管理看注册地址、任务调度日志看每次触发打到哪个地址、执行器侧应用日志交叉验证。
