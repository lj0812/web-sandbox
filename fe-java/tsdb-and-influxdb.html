● 时序数据库 (TSDB)

时序数据库 & InfluxDB

时序数据库专门用来存"随时间不断产生的一串数值"——比如每 10 秒一次的 CPU 使用率、每次请求的耗时、 每分钟一次的传感器读数。它和普通业务数据库(MySQL)的核心区别是：数据几乎只写不改、 按时间批量写入、查询大多是"某个时间范围内的聚合"(求和/平均/最大值)，为此在存储和索引结构上做了专门优化。

02 · 深入 InfluxDB

最主流的独立时序数据库

InfluxDB 是专门为时序场景从零设计的数据库，单机版免费开源，写入性能好、自带类 SQL 的查询语言，是很多监控/IoT 项目的第一选择。

数据模型：拿前端的 JS 对象类比
一条 InfluxDB 数据点长得很像一个带时间戳的对象：{ measurement, tags, fields, timestamp }。 tags 是"用来筛选/分组的标签"（类似给对象打的分类字段，会被索引）， fields 是"实际的数值"（不会被索引，只是数据本身）。
为什么区分 tag 和 field
类似前端里区分"路由参数"（用来定位/筛选）和"表单数据"（承载的内容）。 tag 建了索引，按 tag 过滤（比如 host="server-01"）会很快； field 没有索引，是用来聚合计算的数值本身。
InfluxDB 概念类比说明
Measurement 表名 / 事件名 类似关系型数据库里的"表"，比如 cpu_usage。
Tag 可索引的分类字段 比如 host、region，用来筛选和分组，存的是字符串。
Field 实际数值 比如 usage_percent=87.3，是要被聚合计算的数据本身。
Timestamp 时间戳 每条数据的主键之一，InfluxDB 所有存储和查询都围绕它优化。
Bucket(2.x) 数据库 + 保留策略 2.x 版本里替代了 1.x 的 database，同时定义了数据保留多久（比如 30 天后自动删除）。
写入示例（Line Protocol）
// measurement,tag集合 field集合 时间戳
cpu_usage,host=server-01,region=cn-bj usage_percent=87.3 1691400000000000000
cpu_usage,host=server-02,region=cn-sh usage_percent=42.1 1691400000000000000
查询示例（Flux 语言）
from(bucket: "metrics")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "cpu_usage")
  |> filter(fn: (r) => r.host == "server-01")
  |> aggregateWindow(every: 5m, fn: mean)

03 · 查询语言详解

Flux vs InfluxQL

InfluxDB 有两套查询语言：1.x 时代的 InfluxQL（类 SQL）和 2.x 推出的 Flux（函数式管道）。很多团队两套都在用。

InfluxQL（类 SQL，1.x 原生 / 2.x 兼容）
语法和 SQL 非常像，学习成本低。适合简单聚合查询。不支持跨 bucket 关联、自定义函数等高级操作。
Flux（函数式管道，2.x 原生）
用管道符 |> 串联操作，类似前端的 array.filter().map().reduce() 链式调用。功能更强大，支持跨 bucket JOIN、自定义函数、告警等。
InfluxQL 常用查询
-- 查最近 1 小时 cpu_usage，按 host 过滤
SELECT mean(usage_percent) FROM cpu_usage
  WHERE host = 'server-01' AND time > now() - 1h
  GROUP BY time(5m) fill(none)

-- 查某个 tag 的不同值（相当于 SELECT DISTINCT）
SHOW TAG VALUES FROM cpu_usage WITH KEY = "host"

-- 查最近 10 条原始数据
SELECT * FROM cpu_usage ORDER BY time DESC LIMIT 10

-- 连续查询：每 5 分钟自动聚合写入另一张表（降采样）
CREATE CONTINUOUS QUERY cq_5m ON mydb
  BEGIN
    SELECT mean(usage_percent) INTO cpu_usage_5m
    FROM cpu_usage GROUP BY time(5m), *
  END
Flux 常用查询模式
// 1. 基础查询：最近 1 小时 server-01 的 CPU，每 5 分钟取平均
from(bucket: "metrics")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "cpu_usage")
  |> filter(fn: (r) => r.host == "server-01")
  |> aggregateWindow(every: 5m, fn: mean, createEmpty: false)

// 2. 多 field 计算：CPU 的 max - min 差值
from(bucket: "metrics")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "cpu_usage")
  |> aggregateWindow(every: 10m, fn: spread)

// 3. 分组 Top-N：找出 CPU 最高的 5 台主机
from(bucket: "metrics")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "cpu_usage")
  |> group(columns: ["host"])
  |> mean()
  |> group()
  |> top(n: 5)

// 4. 降采样：把 10 秒粒度降为 1 分钟存到另一个 bucket
from(bucket: "metrics")
  |> range(start: -1d)
  |> filter(fn: (r) => r._measurement == "cpu_usage")
  |> aggregateWindow(every: 1m, fn: mean)
  |> to(bucket: "metrics_downsampled")
对比项InfluxQLFlux
语法风格SELECT ... FROM ... WHEREfrom() |> filter() |> ...
学习成本低（会 SQL 即上手）中（管道式思维，类似 RxJS）
跨 bucket 关联不支持支持 join()
自定义函数不支持支持
告警/任务需外部工具内置 monitor.check()
适用版本1.x 原生，2.x 兼容模式2.x 原生

04 · 写入机制详解

Line Protocol 与批量写入

InfluxDB 的写入围绕 Line Protocol 这一文本格式展开，理解它的结构和批量策略是避免写入问题的关键。

Line Protocol 语法拆解
// 完整格式（每部分用不同分隔符隔开）
//  measurement,tag1=v1,tag2=v2  field1=v1,field2=v2  timestamp
//  ─────┬────  ──────┬──────  ───────┬───────  ────┬────
//    表名    逗号连接的索引标签  空格后是数值字段  纳秒时间戳(可选)

// 示例：一条 HTTP 请求指标
http_req,method=GET,path=/api/users status=200i,latency=42.5,size=1024i 1691400000000000000
//                                  ↑ 整数加 i 后缀   ↑ 浮点数    ↑ 整数加 i

// 字符串 field 值要用双引号
app_log,level=ERROR message="connection refused",code=500i 1691400000000000000

// 不提供时间戳 → 服务端自动用当前时间
cpu_usage,host=server-01 usage_percent=87.3
Field 值类型规则
  • 浮点数：直接写数字，如 42.5
  • 整数：数字后加 i，如 200i
  • 字符串：用双引号包裹，如 "error msg"
  • 布尔值：true / false（或 t/f）
常见写入陷阱
  • 类型冲突：同一 field 第一次写了整数，之后写浮点会报错
  • tag 值爆炸：把 userID 这种高基数值放进 tag 会导致索引膨胀
  • 时间戳精度：默认纳秒，如果传了秒级时间戳会被解释为 1970 年
  • 逗号/空格转义：tag 值里的逗号、空格需要用 \ 转义
批量写入最佳实践
// 批量写入：用换行分隔多条数据，一次 HTTP 请求发送
// POST /api/v2/write?bucket=metrics&precision=ns

cpu_usage,host=server-01 usage_percent=87.3 1691400000000000000
cpu_usage,host=server-02 usage_percent=42.1 1691400000000000000
cpu_usage,host=server-03 usage_percent=63.8 1691400000000000000
mem_usage,host=server-01 used_gb=12.4,total_gb=32.0 1691400000000000000
写入参数建议值说明
单次 batch 大小5000 ~ 10000 条太小 → HTTP 开销大；太大 → 内存压力、超时风险
flush 间隔1s ~ 10s客户端 SDK 攒一批后统一发送的时间窗口
precision（精度）s 或 ms业务不需要纳秒就用秒/毫秒，减少存储开销
gzip 压缩开启Line Protocol 是纯文本，gzip 压缩率通常 > 80%
重试策略指数退避官方 SDK 内置重试，避免写入高峰时打垮服务端
Java 客户端写入示例
// 使用 influxdb-client-java SDK
try (InfluxDBClient client = InfluxDBClientFactory.create(url, token)) {
    WriteApiBlocking writeApi = client.getWriteApiBlocking();

    // 方式 1：直接写 Line Protocol 字符串
    writeApi.writeRecord(WritePrecision.S,
        "cpu_usage,host=server-01 usage_percent=87.3");

    // 方式 2：用 Point 对象构建（推荐，类型安全）
    Point point = Point.measurement("cpu_usage")
        .addTag("host", "server-01")
        .addField("usage_percent", 87.3)
        .time(Instant.now(), WritePrecision.S);
    writeApi.writePoint(point);

    // 方式 3：批量写入（异步，生产环境推荐）
    try (WriteApi asyncWrite = client.makeWriteApi(
            WriteOptions.builder()
                .batchSize(5000)
                .flushInterval(1000)  // 1秒 flush 一次
                .build())) {
        for (MetricData m : metricsList) {
            asyncWrite.writePoint(toPoint(m));
        }
    } // close 时自动 flush 剩余数据
}

05 · 超时原因分析

InfluxDB 超时的常见场景与排查

InfluxDB 在生产环境中遇到超时是比较常见的问题，通常集中在查询超时和写入超时两大类。

超时分类地图
查询超时
扫描数据量过大 / 没用时间范围 / series 过多
|
写入超时
batch 过大 / 磁盘 IO 瓶颈 / 内存不足
|
连接超时
网络抖动 / 连接池耗尽 / 负载均衡配置
一、查询超时（最常见）
原因症状解决方案
时间范围过大 查 30 天甚至全量数据，扫描行数上亿 始终加 WHERE time > now() - 合理范围；Flux 里始终用 range()
没有按 tag 过滤 全量扫描所有 series 查询条件里优先使用 tag（有索引）过滤，避免只用 field 条件
series 基数爆炸 tag 组合数（series）达百万级，内存暴涨 避免把 userID、traceID 等高基数值放进 tag；用 SHOW SERIES CARDINALITY 排查
聚合粒度太细 对百万数据点做逐秒聚合，计算量巨大 增大聚合窗口（如 5m、1h）；用降采样预聚合
正则匹配 tag WHERE host =~ /prod.*/ 无法利用索引 尽量用精确匹配；如需模糊匹配，缩小时间范围
二、写入超时
原因症状解决方案
单次 batch 过大 一次发送几十万条数据，HTTP body 几十 MB 控制每批 5000~10000 条；开启 gzip 压缩
磁盘 IO 饱和 写入延迟周期性升高，iostat 显示 %util ≈ 100% 换 SSD；InfluxDB 的 WAL 和数据目录分不同磁盘
compaction 积压 TSM 文件合并赶不上写入速度 调大 compact-throughput-burst；降低写入频率或拆分实例
内存不足（OOM） 写入时进程被 kill 或出现 cache-max-memory-size 告警 增大内存；调整 cache-max-memory-size（默认 1GB）
series 高基数写入 持续产生新 series 导致索引不断膨胀 设计 tag 时严格控制基数；设置 max-series-per-database
三、连接超时
原因症状解决方案
客户端超时设置过短 正常查询被客户端提前断开 Java SDK 调大 okHttpClient.readTimeout；Grafana 调大 timeout
HTTP 连接池耗尽 高并发时 ConnectionPoolTimeoutException 增大连接池 maxIdleConnections；复用 client 实例
LB / 网关超时 Nginx/Kong 返回 504，InfluxDB 日志里无对应请求 调大反向代理的 proxy_read_timeout（默认常为 60s）
排查超时的实用命令
-- 查看当前 series 基数（最重要的健康指标之一）
SHOW SERIES CARDINALITY
SHOW SERIES CARDINALITY ON mydb

-- 查看各 measurement 的 series 数量
SHOW SERIES CARDINALITY FROM cpu_usage

-- 查看当前正在执行的查询（找出慢查询）
SHOW QUERIES

-- 强制终止一个慢查询
KILL QUERY 42

-- 查看 shard 信息（判断数据分布是否均匀）
SHOW SHARDS

-- 查看保留策略（数据是否按预期过期清理）
SHOW RETENTION POLICIES ON mydb

06 · Series 基数——性能的关键

理解高基数问题

InfluxDB 里 90% 的性能问题都和 series 基数有关，这是使用 InfluxDB 最需要理解的概念。

什么是 Series
一个 series = measurement + 所有 tag 的唯一组合。可以类比为前端里的"组合 key"。 
// 假设 measurement = cpu_usage，tag 有 host 和 region
// 10 台 host × 3 个 region = 30 个 series（可控）
cpu_usage,host=s01,region=bj  →  series #1
cpu_usage,host=s01,region=sh  →  series #2
...

// 如果把 request_id 放进 tag：
// 每个请求都是新 series → 一天几百万 series（灾难）
http_req,request_id=abc123  →  series #999999...
健康基数参考
  • < 10 万：单机轻松应对
  • 10 ~ 100 万：需要关注内存，建议 16GB+
  • > 100 万：性能明显下降，需拆库或降基数
  • > 1000 万：基本不可用，OOM 频发
降低基数的方法
  • 高基数值（userID、traceID）放 field 而非 tag
  • 对连续值做分桶：latency 从精确值 → 0-100ms/100-500ms
  • 设置 max-series-per-database 做硬限制保护
  • 定期清理不再写入的过期 series

07 · 保留策略与降采样

数据生命周期管理

时序数据通常"越新越有价值"，InfluxDB 通过保留策略 (RP) 和降采样实现自动清理和压缩。

典型生命周期策略
原始数据（10s 粒度）
保留 7 天
→
降采样（5min 粒度）
保留 30 天
→
再降采样（1h 粒度）
保留 1 年
→
自动删除
到期即清理
1.x 保留策略配置
-- 创建 7 天保留策略
CREATE RETENTION POLICY rp_7d
  ON mydb DURATION 7d
  REPLICATION 1 DEFAULT

-- 创建 30 天保留策略
CREATE RETENTION POLICY rp_30d
  ON mydb DURATION 30d
  REPLICATION 1
2.x Bucket + Task 降采样
// 创建 bucket 时指定保留时间
// bucket: metrics (7d)
// bucket: metrics_30d (30d)

// 用 Task 定时降采样
option task = {name: "downsample",
  every: 5m}

from(bucket: "metrics")
  |> range(start: -task.every)
  |> aggregateWindow(
       every: 5m, fn: mean)
  |> to(bucket: "metrics_30d")

08 · 什么时候选 InfluxDB

优势与局限

适合
  • 监控告警、IoT 设备数据、应用性能指标这类高频写入、按时间聚合查询的场景
  • 想要"开箱即用"，不想自己维护 PostgreSQL/ClickHouse 这类通用数据库
  • 和 Telegraf / Grafana 生态搭配，几乎零配置起步
不适合
  • 需要和普通业务表做复杂 JOIN 的场景 —— 这种更适合 TimescaleDB
  • 数据量特别大、要做复杂多维分析（这时 ClickHouse 通常更快、更省资源）
  • 需要强事务、频繁更新/删除单条数据的场景（时序库普遍只擅长追加写入）
