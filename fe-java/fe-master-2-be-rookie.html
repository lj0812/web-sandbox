前端高手 → 后端新手

梳理 Java / Spring Boot 中那些"前端心智模型里完全没有"或"形态截然不同"的核心概念。 每个概念都配有 Java 代码、与前端世界最接近的类比（以及类比在哪里失效），帮助你快速建立后端思维。

框架层 · 01

依赖注入 (DI) 与 IoC 容器

把"自己 new 对象"变成"框架给你塞对象"

概念与问题

在前端里，你需要某个工具/服务时通常直接 import 然后 new 或调用。 在 Spring 里，你几乎不手动 new 业务对象——所有对象（称为 Bean）的创建、生命周期管理和依赖关系都交给 IoC 容器（Inversion of Control，控制反转）来处理。DI（依赖注入）是 IoC 的实现手段： 容器在创建对象时，自动把它需要的其他对象"注入"进去。

这解决的核心问题是：解耦。当 A 依赖 B 时，A 不需要知道 B 是怎么创建的，也不需要知道 B 的具体实现类是什么。 只要声明"我需要一个 B"，容器就会找到合适的实例塞给你。

Java 代码示例
@Service
public class OrderService {

    // 不需要 new UserService()——Spring 容器自动注入
    private final UserService userService;

    // 构造器注入（推荐方式）
    public OrderService(UserService userService) {
        this.userService = userService;
    }

    public Order createOrder(Long userId) {
        User user = userService.findById(userId);
        // ...
    }
}

// 接口 + 实现分离：想换实现只需改注解，调用方完全不知道
public interface UserService {
    User findById(Long id);
}

@Service
public class UserServiceImpl implements UserService {
    public User findById(Long id) { /* 查数据库 */ }
}
前端类比：Vue 3 的 provide / inject
祖先组件 provide('userService', service)，子孙组件 inject('userService') 获取——不需要层层 props 传递。
类比在哪里失效：Vue 的 provide/inject 是组件树层级的、手动显式调用的，作用域有限。 Spring IoC 是一个全局容器，在应用启动时扫描所有类，自动发现、自动注入、自动管理生命周期，规模和能力完全不在一个量级。 前端没有"容器统一管理所有模块实例"这个概念。
不掌握会踩的坑： 手动 new OrderService() 创建对象——这个对象不受 Spring 管理，里面所有 @Autowired 字段全是 null，运行时直接 NPE。 这是 Java 新手最高频的错误，因为前端思维里"new 一个对象用"是天经地义的。

框架层 · 02

Bean 生命周期与作用域

对象什么时候出生、什么时候死、在整个应用里有几个

概念与问题

Spring 容器管理的每个对象叫 Bean。每个 Bean 有完整的生命周期——从创建 → 属性注入 → 初始化回调 → 就绪可用 → 销毁回调—— 框架在每个阶段都给你钩子介入。此外，Bean 有作用域 (Scope)，决定容器为这个 Bean 创建几个实例：

作用域含义使用场景
Singleton整个应用只有一个实例（默认）绝大多数 Service、Repository
Prototype每次注入/获取都新建一个需要独立状态的对象，如报表生成器
Request每个 HTTP 请求一个实例存放请求级别上下文
Session每个用户会话一个实例购物车等会话状态
Java 代码示例
@Component
public class CacheManager {

    // 初始化回调：Bean 创建 + 注入完成后执行
    @PostConstruct
    public void init() {
        System.out.println("缓存初始化完毕");
    }

    // 销毁回调：应用关闭时执行
    @PreDestroy
    public void cleanup() {
        System.out.println("释放缓存资源");
    }
}

// Prototype 作用域：每次注入都是新实例
@Component
@Scope("prototype")
public class ReportBuilder {
    private List<String> rows = new ArrayList<>();
}
前端类比：Vue 组件生命周期 (onMounted / onUnmounted)
Vue 组件也有"创建 → 挂载 → 卸载"的生命周期钩子。
类比在哪里失效：Vue 组件生命周期跟随 DOM 和用户交互——用户切换路由，组件就销毁重建。 Spring Bean 默认是 Singleton，应用启动时创建，直到进程退出才销毁——一个 Bean 可能存活数天甚至数月。 "作用域"的概念在前端完全没有对应物，因为前端不需要考虑"一个服务对象在多个并发请求间共享"的问题。
不掌握会踩的坑： 在 Singleton Bean 里存放请求级别的可变状态（比如 private User currentUser;）， 结果多个请求并发时互相覆盖数据——因为所有请求共享同一个实例。 前端单线程 + 每个用户独立运行，天然不存在这个问题。

框架层 · 03

注解驱动开发与反射机制

用"标签"声明意图，框架通过反射在运行时解读并执行

概念与问题

Java 的注解 (Annotation) 形如 @Service、@Autowired、@Transactional， 是附着在类/方法/字段上的元数据标签。注解本身不执行任何代码——它们靠反射 (Reflection) 机制在运行时被框架读取并触发对应的行为。

反射是 Java 独有的强大能力：在运行时可以"照镜子"——检查类有哪些字段、方法、注解，甚至动态调用私有方法、修改私有字段。 Spring 几乎所有魔法（DI、AOP、事务）都建立在反射之上。

Java 代码示例
// 常见注解及其作用
@RestController          // 标记：这是一个 HTTP 接口控制器
@RequestMapping("/api")  // 标记：路由前缀是 /api
public class UserController {

    @Autowired               // 标记：请注入 UserService 实例
    private UserService userService;

    @GetMapping("/users/{id}") // 标记：GET /api/users/123
    public User getUser(@PathVariable Long id) {
        return userService.findById(id);
    }
}

// 反射示例：在运行时获取类信息
Class<?> clazz = UserController.class;
Method[] methods = clazz.getDeclaredMethods();
for (Method m : methods) {
    if (m.isAnnotationPresent(GetMapping.class)) {
        GetMapping gm = m.getAnnotation(GetMapping.class);
        System.out.println("路由: " + gm.value()[0]);
    }
}
前端类比：TS 装饰器 (Decorators) — 实验性/较少使用
TypeScript 的 @Log 装饰器语法看起来和 Java 注解很像，Vue Class Component 里也用过。
类比在哪里失效：① TS 装饰器在编译时就被转换成函数调用了，不存在运行时"照镜子"的反射能力。 ② JavaScript 语言本身没有反射机制——无法在运行时检查一个函数有几个参数叫什么名字、有哪些注解。 Java 反射是语言级别的能力，允许框架在运行时做"自动发现、自动装配"，这是前端没有的全新心智模型。
不掌握会踩的坑： ① 随意自定义注解却不写对应的处理器，结果注解毫无效果——注解只是标签，没有处理逻辑就是摆设。 ② 不理解注解的生效范围：比如 @Transactional 只在被 Spring 代理调用时才有效，同一个类内部方法直接调用时注解不生效（参见 AOP 章节）。

框架层 · 04

AOP 面向切面编程

把"横跨多个业务方法的通用逻辑"抽出来，一处编写处处生效

概念与问题

日志记录、权限校验、性能统计、事务管理——这些逻辑和具体业务无关，但几乎每个方法都需要。 如果手动在每个方法里写，代码到处重复。AOP 的思路是：把这些横切关注点 (Cross-cutting Concerns) 单独抽成一个"切面"， 通过配置声明"在哪些方法执行前/后/异常时自动插入这段逻辑"。

Spring AOP 底层通过动态代理实现——你调用的 userService.findById() 其实不是原始对象， 而是 Spring 生成的代理对象，代理在调用前后插入切面逻辑。

Java 代码示例
@Aspect
@Component
public class LoggingAspect {

    // 切入点：所有 service 包下的公共方法
    @Around("execution(* com.example.service.*.*(..))")
    public Object logMethod(ProceedingJoinPoint joinPoint) throws Throwable {
        String method = joinPoint.getSignature().getName();
        long start = System.currentTimeMillis();

        try {
            Object result = joinPoint.proceed(); // 执行原始方法
            long ms = System.currentTimeMillis() - start;
            log.info("{}() 耗时 {}ms", method, ms);
            return result;
        } catch (Exception e) {
            log.error("{}() 异常: {}", method, e.getMessage());
            throw e;
        }
    }
}
前端类比：Vue Router 的全局路由守卫 / Axios 请求拦截器
router.beforeEach((to, from, next) => { ... }) 就是一种 AOP 思想——在"每次路由跳转"前后统一插入逻辑。 Axios 的 interceptors.request.use() 也类似。
类比在哪里失效：前端的拦截器只能用在"框架提供了拦截点"的地方（路由、HTTP 请求），无法拦截任意函数调用。 Spring AOP 通过动态代理，可以自动拦截任何被 Spring 管理的方法——你写个注解 @Audit 加到任何方法上， 就能自动记录审计日志。这种"对任意方法透明插入逻辑"的能力是前端没有的。
不掌握会踩的坑： ① 自调用失效：在同一个类里 this.methodB() 调用，AOP 不会生效，因为走的不是代理对象。这是最经典的坑。 ② 不理解代理机制，在 debug 时发现调用栈里多了一层 CGLIB 代理类而感到困惑。

框架层 · 05

事务管理

一组数据库操作要么全部成功，要么全部回滚——不存在"做了一半"

概念与问题

前端调接口基本只关心"请求成功或失败"。后端要直接操作数据库，一个业务可能涉及多条 SQL（扣余额 + 加积分 + 写日志）， 如果中间某步失败，之前的操作必须回滚，否则数据就不一致了。这就是事务 (Transaction) 要解决的问题。

ACID 四大特性：Atomicity（原子性）、Consistency（一致性）、Isolation（隔离性）、Durability（持久性）。 Spring 还引入了传播机制（一个事务方法调用另一个事务方法时，合并还是新开？）和回滚规则。

Java 代码示例
@Service
public class PaymentService {

    // 加一个注解就开启事务——底层由 AOP + 数据库连接池协作完成
    @Transactional(rollbackFor = Exception.class)
    public void pay(Long userId, BigDecimal amount) {
        accountDao.deductBalance(userId, amount);  // 扣余额
        pointsDao.addPoints(userId, 100);          // 加积分
        orderDao.updateStatus(orderId, "PAID");   // 改状态
        // 如果任何一步抛异常 → 三条 SQL 全部回滚
    }
}

// 传播机制示例
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeAuditLog(String msg) {
    // 即使外层事务回滚，审计日志也要保存 → 新开独立事务
    auditDao.insert(msg);
}
传播机制行为典型场景
REQUIRED（默认）有事务就加入，没有就新开大多数业务方法
REQUIRES_NEW总是新开独立事务审计日志、通知（不受外层回滚影响）
NESTED在现有事务里创建保存点部分失败可回滚到保存点
NOT_SUPPORTED挂起当前事务，以非事务方式执行纯查询操作
这是前端没有的全新心智模型
前端不直接操作数据库，没有"多条操作要么全成功要么全回滚"的场景。 最接近的类比可能是 localStorage 里自己做的乐观更新 + 回退逻辑，但那是手动的、不可靠的。 后端事务是数据库引擎级别的保证，具有严格的 ACID 特性。
核心差异：前端出错最多 UI 状态错误刷新就好；后端出错数据永久损坏——所以事务是后端最关键的安全网。
不掌握会踩的坑： ① @Transactional 默认只对 RuntimeException 回滚，受检异常（如 IOException）不回滚——必须加 rollbackFor = Exception.class。 ② 同类内部方法互调事务不生效（AOP 代理陷阱，同第 4 节）。 ③ 事务范围过大，一个方法里又调 HTTP 又操作数据库，长事务锁住数据库连接导致连接池耗尽。

框架层 · 06

ORM 对象-关系映射

让 Java 对象和数据库表自动对应，不用手写 SQL（或少写 SQL）

概念与问题

数据库里是表和行（关系型数据），Java 里是类和对象（面向对象数据）。两者结构不同需要转换。 ORM (Object-Relational Mapping) 就是这层转换器：你操作 Java 对象，框架自动翻译成 SQL 去操作数据库。

主流有两个流派：JPA/Hibernate（全自动，Java 对象直接映射到表，几乎不写 SQL）和 MyBatis（半自动，SQL 手写但结果自动映射到对象）。

Java 代码示例
JPA/Hibernate（全自动）
@Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue
    private Long id;

    @Column(nullable = false)
    private String name;

    @OneToMany(mappedBy = "user")
    private List<Order> orders;
}

// Spring Data JPA：声明接口即可
public interface UserRepository
    extends JpaRepository<User, Long> {
    List<User> findByName(String n);
    // 框架自动生成 SQL!
}
MyBatis（半自动，手写 SQL）
// Mapper 接口
@Mapper
public interface UserMapper {

  @Select("SELECT * FROM users
    WHERE name = #{name}")
  List<User> findByName(
      String name
  );

  @Insert("INSERT INTO users
    (name, email)
    VALUES (#{name}, #{email})")
  void insert(User user);
}
前端类比：Prisma / TypeORM（Node.js 生态）
如果你用过 Prisma 的 prisma.user.findMany()，那和 Spring Data JPA 的体验非常相似。
类比在哪里失效：前端很少直接操作数据库，即使在 Node.js 全栈项目里，ORM 的复杂度也远不及 Java 生态： Java ORM 有一级/二级缓存、延迟加载 (Lazy Loading)、级联操作、乐观锁/悲观锁等大量概念。 特别是 Hibernate 的 Lazy Loading 和 N+1 查询问题，是后端性能调优的重灾区。
不掌握会踩的坑： ① N+1 问题：查 10 个用户，每个用户的订单再各查一次 → 共 11 条 SQL。正确做法是用 JOIN FETCH 一次查出。 ② Lazy Loading 异常：JPA 默认关联对象延迟加载，在事务关闭后访问关联属性直接报 LazyInitializationException。 ③ 不熟悉 SQL 就用 JPA 自动生成的 SQL，结果全表扫描却不知道——后端必须学会看执行计划。

框架层 · 07

分层架构 (Controller / Service / Repository)

强制的三层分工——接收请求 / 处理业务 / 访问数据

概念与问题

Spring Boot 项目几乎都遵循经典三层架构，每一层职责明确，不允许跨层调用。 这不是语言强制的，但是社区约定和团队规范——不遵守就会被 code review 打回。

层注解职责类比前端
Controller @RestController 接收 HTTP 请求、参数校验、调用 Service、返回响应 Vue 组件的事件处理 / API 路由定义
Service @Service 核心业务逻辑、事务边界 composable / store 里的业务逻辑
Repository / DAO @Repository 数据库访问，封装 SQL api.ts 里的 fetch 封装
Java 代码示例
// 请求入口 → Controller（只做转发和格式化）
@RestController
@RequestMapping("/api/users")
public class UserController {
    private final UserService userService;
    // 构造器注入省略...

    @GetMapping("/{id}")
    public UserVO getUser(@PathVariable Long id) {
        return userService.getUserById(id); // 只调 Service
    }
}

// 业务逻辑 → Service（核心计算、流程编排）
@Service
public class UserService {
    private final UserRepository userRepo;

    @Transactional(readOnly = true)
    public UserVO getUserById(Long id) {
        User user = userRepo.findById(id)
            .orElseThrow(() -> new NotFoundException("用户不存在"));
        return toVO(user); // Entity → VO 转换
    }
}

// 数据访问 → Repository（只管 CRUD）
public interface UserRepository extends JpaRepository<User, Long> {
}
前端类比：组件 → composable/store → api 的分层
Vue 项目也有类似分层：组件调 composable/store，store 调 api。
类比在哪里失效：前端的分层是"建议"而非"约定"，小项目经常组件里直接 fetch 也没什么问题。 后端的分层是强约定，而且有额外的数据转换概念：Entity（数据库对象）、DTO（传输对象）、VO（视图对象）之间需要互相转换。 这种"同一个数据在不同层有不同的表示形态"在前端几乎不存在。
不掌握会踩的坑： ① Controller 里直接写 SQL 或业务逻辑 → 代码耦合，无法单测，review 被拒。 ② 直接把数据库 Entity 返给前端 → 敏感字段泄露（密码哈希）、Lazy Loading 在 JSON 序列化时触发异常。

框架层 · 08

Spring Security 与权限体系

一套完整的认证（你是谁）+ 授权（你能干什么）框架

概念与问题

前端的"权限控制"通常是路由守卫 + 按钮显隐，本质是 UI 层面的。真正的安全防线在后端： Spring Security 提供了认证 (Authentication)——验证用户身份（登录），和授权 (Authorization)——控制用户能访问哪些资源。 它通过一条过滤器链拦截每个 HTTP 请求，在请求到达 Controller 之前就完成安全检查。

Java 代码示例
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .sessionManagement(s -> s
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
            )
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}

// 方法级别的权限控制
@PreAuthorize("hasRole('ADMIN') or #userId == authentication.principal.id")
public User getUser(Long userId) { /* ... */ }
前端类比：Vue Router 路由守卫 + v-permission 指令
router.beforeEach 检查登录状态、v-if="hasPermission('admin')" 控制按钮显隐。
类比在哪里失效：前端的权限控制是"可以被绕过"的——用户可以直接调 API。后端的 Spring Security 是真正的安全屏障， 未授权的请求在到达业务代码之前就会被拦截返回 401/403。此外 Spring Security 还涉及密码加密存储 (BCrypt)、 CSRF 防护、Session 管理、OAuth2 集成等一整套体系，远比前端的权限控制复杂。
不掌握会踩的坑： ① 引入 spring-boot-starter-security 后所有接口直接 403——因为默认配置要求所有请求都认证。 ② 忘记配置 CORS，前端跨域请求全被 Security 拦截。 ③ 把权限判断只做在前端，后端接口裸奔——安全审计直接不过。

框架层 · 09

拦截器与过滤器链

请求从进入服务器到到达业务代码之间经过的层层关卡

概念与问题

一个 HTTP 请求到达 Spring Boot 应用后，会经历两道不同层次的"中间件"： Filter（Servlet 规范级别，最先执行）和 Interceptor（Spring MVC 级别，在 Filter 之后）。 两者都能在请求处理前后插入逻辑，但作用层次和能力不同。

对比项Filter（过滤器）Interceptor（拦截器）
规范层级Servlet 规范（Java EE）Spring MVC 层
执行顺序更早更晚（Filter 之后）
能否访问 Spring Bean需额外配置可以直接注入
典型用途编码转换、CORS、日志、压缩登录校验、权限、审计
Java 代码示例
// Filter 示例：记录每个请求的耗时
@Component
public class TimingFilter implements Filter {
    @Override
    public void doFilter(ServletRequest req, ServletResponse res,
                         FilterChain chain) throws IOException, ServletException {
        long start = System.currentTimeMillis();
        chain.doFilter(req, res); // 放行，继续后续链路
        long ms = System.currentTimeMillis() - start;
        log.info("请求耗时: {}ms", ms);
    }
}

// Interceptor 示例：登录校验
@Component
public class AuthInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res,
                              Object handler) {
        String token = req.getHeader("Authorization");
        if (token == null) {
            res.setStatus(401);
            return false; // 中断请求
        }
        return true; // 放行
    }
}
前端类比：Express / Koa 的中间件 (middleware)
Express 的 app.use((req, res, next) => { ... next() }) 机制——层层传递，每一层都可以选择放行或中断。
类比在哪里失效：Express 中间件是一条线性链。Spring 是Filter 链 + Interceptor 链双层结构， 还有 Spring Security 自己的 15+ 个 Filter。理解整个请求生命周期的调用顺序比前端复杂很多。
不掌握会踩的坑： ① Filter 和 Interceptor 搞混——在 Interceptor 里做编码转换没效果（请求体在 Filter 层就已经被读取了）。 ② 不知道 Filter 的 chain.doFilter() 是必须调用的——忘记调就等于吞掉了请求。

框架层 · 10

配置管理与多环境 Profile

一套代码跑开发/测试/生产——靠配置文件切换环境

概念与问题

Spring Boot 用 application.yml（或 .properties）集中管理所有配置。 通过 Profile 机制，可以为不同环境准备不同的配置文件：application-dev.yml、 application-prod.yml，启动时指定 --spring.profiles.active=prod 即可切换。

Java 代码示例
# application.yml（公共配置）
server:
  port: 8080
spring:
  profiles:
    active: dev  # 默认使用 dev 环境

# application-dev.yml
spring.datasource:
  url: jdbc:mysql://localhost:3306/mydb
  username: root

# application-prod.yml
spring.datasource:
  url: jdbc:mysql://prod-rds.amazonaws.com:3306/mydb
  username: app_user
// 在代码里读取配置值
@Value("${spring.datasource.url}")
private String dbUrl;

// 根据 Profile 条件化注册 Bean
@Bean
@Profile("dev")
public DataSource devDataSource() {
    // 开发环境用内存数据库 H2
}

@Bean
@Profile("prod")
public DataSource prodDataSource() {
    // 生产环境用 MySQL 连接池
}
前端类比：.env.development / .env.production + Vite 的 import.meta.env
Vite 项目里也有多环境配置文件，通过 import.meta.env.VITE_API_URL 读取。
类比在哪里失效：前端的 .env 只是简单的 key-value 字符串替换，在构建时就确定了。 Spring 的 Profile 系统在运行时决定使用哪个配置文件，可以按 Profile 条件注册不同的 Bean、 加载不同的数据库连接、启用不同的功能模块——是一套完整的运行时配置管理体系。
不掌握会踩的坑： ① 本地能跑但部署到测试环境报错——因为忘记配置对应 Profile 的数据库地址 / Redis 地址。 ② 把敏感信息（密码、密钥）写死在 application.yml 里提交到 Git——应该用环境变量或配置中心。

框架层 · 11

构建工具与依赖管理 (Maven / Gradle)

后端的 package.json + npm，但更重、更规范

概念与问题

Java 没有 npm install。它用 Maven（XML 配置，最主流）或 Gradle（Groovy/Kotlin DSL，Android 常用）来管理依赖和构建。 依赖声明在 pom.xml（Maven）或 build.gradle 中，从中央仓库（Maven Central，类似 npmjs.com）下载 JAR 包。

代码示例
Maven pom.xml ≈ package.json

依赖 scope（npm 没有的概念）
Maven 的 scope 控制依赖在

         ≈ npm dependencies

         （编译时不参与）

前端类比：npm / pnpm + Vite 构建

类比在哪里失效：① Maven 的依赖用 groupId + artifactId + version 三元组定位（类似 @scope/package@version 但更严格）。 ② Java 有 provided scope（"我编译时要用但运行时别人会给"），这在前端不存在。 ③ Maven 还是项目的构建/打包工具——编译 Java 源码、运行测试、打成可执行 JAR，远不只是一个包管理器。

运行时层 · 01

JVM 内存模型

Java 程序在虚拟机里的内存是分区管理的——堆、栈、方法区各司其职

概念与问题

JavaScript 引擎（V8）对开发者屏蔽了内存细节。Java 的 JVM 把内存划分为多个区域， 每个区域有不同的用途和回收策略。后端开发经常需要调整这些区域的大小来排查 OOM（内存溢出）问题。

内存区域存什么大小溢出异常
堆 (Heap)所有对象实例、数组JVM 内存最大的区域，可配置OutOfMemoryError: Java heap space
栈 (Stack)每个线程的方法调用帧（局部变量、方法参数）每个线程私有，通常 512K~1MStackOverflowError
方法区 / 元空间类的元信息、常量、静态变量JDK 8+ 使用本地内存OutOfMemoryError: Metaspace
Java 代码示例
// 启动参数控制内存分配
// java -Xms512m -Xmx2g -Xss1m -XX:MetaspaceSize=256m MyApp
//  -Xms：初始堆大小    -Xmx：最大堆大小
//  -Xss：每个线程栈大小  -XX:MetaspaceSize：方法区初始大小

// 堆溢出示例
List<byte[]> list = new ArrayList<>();
while (true) {
    list.add(new byte[1024 * 1024]); // 每次分配 1MB
    // 最终 → OutOfMemoryError: Java heap space
}

// 栈溢出示例
public void infiniteRecursion() {
    infiniteRecursion(); // 无限递归 → StackOverflowError
}
这是前端没有的全新心智模型
V8 引擎也有堆和栈，但对 JS 开发者完全透明——你不需要设置内存大小、不需要区分对象在堆还是栈、不需要关心方法区。
核心差异：后端 JVM 一个进程可能分配 4GB~32GB 内存，跑数天到数月不重启。 内存分配不合理会导致频繁 GC（卡顿）或 OOM（进程崩溃）。这是后端性能调优和线上排障的基础知识。
不掌握会踩的坑： ① 不设 -Xmx，JVM 默认用物理内存的 1/4，Docker 容器里可能直接 OOM 被 kill。 ② 不了解堆/栈区别，排查不出是内存泄漏（堆）还是递归过深（栈）。

运行时层 · 02

垃圾回收 (GC) 机制

JVM 自动回收不再使用的对象内存——但它何时回收、暂停多久，你需要关心

概念与问题

JavaScript 也有 GC，但 V8 的 GC 暂停通常只有几毫秒，前端开发者几乎无感。 Java 的 GC 需要管理的内存规模大得多（GB 级），GC 暂停（Stop-the-World）可能达到数百毫秒甚至秒级， 直接影响接口响应时间。选择合适的 GC 算法和调优参数是后端必修课。

GC 收集器特点适用场景
G1（JDK 9+ 默认）分区收集，可预测暂停时间大多数后端服务
ZGC超低延迟（暂停 < 1ms），适合超大堆延迟敏感的在线服务
Parallel GC吞吐量优先，暂停时间长批处理 / 数据计算
Java 代码示例
// GC 调优启动参数示例
// 使用 G1，目标暂停时间 200ms，打印 GC 日志
// java -XX:+UseG1GC -XX:MaxGCPauseMillis=200
//      -Xlog:gc*:file=gc.log:time MyApp

// 内存泄漏的典型模式：静态集合不断增长
public class CacheHolder {
    // static 集合生命周期和应用一样长
    // 不断 put 却从不 remove → 内存泄漏
    private static final Map<String, Object> cache = new HashMap<>();

    public static void put(String key, Object val) {
        cache.put(key, val); // GC 永远回收不了这些对象
    }
}
前端类比：V8 的垃圾回收
JavaScript 也有 GC（标记-清除），而且大部分时候无感知。
类比在哪里失效：前端 V8 管理的内存通常不超过 1.5GB，而且页面刷新就释放了。 后端 JVM 可能管理 32GB 堆内存，运行数月不重启。GC 暂停会导致所有请求卡住， 对于高并发服务来说，GC 调优是一个专门的技术领域——有自己的术语（Young/Old 分代、 Minor/Major/Full GC、GC Roots、安全点）和诊断工具链。
不掌握会踩的坑： ① 线上服务每隔一段时间响应突然变慢 → 多半是 Full GC 导致的 Stop-the-World 暂停。 ② 不知道用 jstat、jmap、MAT 排查内存问题，只能重启服务。 ③ 内存泄漏导致 OOM 但不会看 GC 日志定位根因。

运行时层 · 03

多线程与线程安全

前端单线程无并发之忧，后端多线程的世界里处处是坑

概念与问题

JavaScript 是单线程 + 事件循环——同一时刻只有一段代码在执行，你永远不用担心两段代码同时修改同一个变量。 Java 后端是多线程的——每个 HTTP 请求在一个独立的线程中处理，多个请求可能同时执行同一段代码、 访问同一个共享变量。这引出了整个"线程安全"的问题域：竞态条件、死锁、可见性。

Java 代码示例
// 线程不安全的典型示例
public class Counter {
    private int count = 0;

    // 多个线程同时调用 → 结果不确定（竞态条件）
    public void increment() {
        count++; // 看起来一步操作，实际是 读-改-写 三步
    }
}

// 线程安全的写法
public class SafeCounter {
    private final AtomicInteger count = new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet(); // 原子操作，线程安全
    }
}

// synchronized 关键字：同一时刻只有一个线程能执行这个方法
public synchronized void transfer(Account from, Account to, int amount) {
    from.deduct(amount);
    to.add(amount);
}

// ConcurrentHashMap：线程安全的 Map（普通 HashMap 多线程下会死循环）
Map<String, Object> map = new ConcurrentHashMap<>();
这是前端没有的全新心智模型
JavaScript 单线程模型天然避免了并发问题。即使有 Web Worker，也是通过消息传递通信，不共享内存。
核心差异：后端一个 Spring Boot 应用默认 200 个线程同时处理请求，它们共享同一份 Service 对象和同一份内存。 任何共享的可变状态（实例变量、静态变量、共享集合）都是潜在的并发炸弹。 这需要建立一套全新的思维：不可变优先 → 无锁原子类 → 细粒度锁 → 并发集合。
不掌握会踩的坑： ① 在 Singleton Bean 里用 HashMap 做缓存 → 多线程并发写导致死循环、CPU 100%。应该用 ConcurrentHashMap。 ② 用 SimpleDateFormat（非线程安全）做日期格式化 → 并发下日期错乱。应该用 DateTimeFormatter。 ③ 前端习惯用全局变量存状态 → 后端这么做直接数据串号。

运行时层 · 04

线程池

预先创建一组线程复用，而不是每次都创建销毁——线程的"对象池"

概念与问题

创建线程的开销很大（分配栈内存、OS 调度）。如果每个请求都 new Thread() 处理， 高并发下会耗尽系统资源。线程池预先创建一组线程，任务来了从池中取线程执行，执行完归还—— 像一个固定大小的"工位"，有空工位就分配，没空就排队等。

Java 代码示例
// Spring Boot 中配置线程池用于异步任务
@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);      // 核心线程数
        executor.setMaxPoolSize(50);       // 最大线程数
        executor.setQueueCapacity(200);    // 等待队列容量
        executor.setKeepAliveSeconds(60);  // 空闲线程存活时间
        executor.setRejectedExecutionHandler(
            new ThreadPoolExecutor.CallerRunsPolicy() // 拒绝策略
        );
        executor.initialize();
        return executor;
    }
}

// 使用：标记方法为异步执行
@Async
public void sendEmail(String to, String body) {
    // 在线程池中执行，不阻塞主请求线程
    mailSender.send(to, body);
}
前端类比：浏览器的 HTTP 并发限制 (6 connections per host)
浏览器对同一域名最多维持 6 个 TCP 连接——超出的请求排队。这本质上是一种"连接池"的思想。
类比在哪里失效：浏览器连接池对开发者透明且不可配置。后端的线程池需要你手动设置核心线程数、最大线程数、 队列大小、拒绝策略——设小了任务排队超时，设大了内存耗尽。这是后端容量规划的核心参数。
不掌握会踩的坑： ① 用 Executors.newCachedThreadPool()（无上限）→ 高并发下创建上万线程 OOM。 ② 线程池队列满了不知道怎么处理 → 默认 AbortPolicy 直接抛异常丢弃任务。 ③ 不理解 @Async 底层就是线程池 → 不配置线程池参数就用默认的，生产环境性能不可控。

运行时层 · 05

数据库连接池

提前建好一批数据库连接复用，而不是每次查询都重新握手

概念与问题

建立数据库连接需要 TCP 三次握手 + 认证 + 协议协商，耗时可达几十毫秒。如果每次 SQL 查询都建新连接， 性能完全不可接受。连接池（如 HikariCP——Spring Boot 默认使用）预先创建并维持一批数据库连接， 业务代码从池中"借"连接用，用完"还"回去。

Java 代码示例
# application.yml — HikariCP 连接池配置
spring.datasource:
  url: jdbc:mysql://localhost:3306/mydb
  username: root
  password: secret
  hikari:
    minimum-idle: 5           # 最小空闲连接数
    maximum-pool-size: 20     # 最大连接数
    connection-timeout: 3000  # 获取连接超时（ms）
    idle-timeout: 600000      # 空闲连接存活时间（10min）
    max-lifetime: 1800000     # 连接最大生命周期（30min）
    leak-detection-threshold: 60000 # 连接泄漏检测（1min）
前端类比：HTTP Keep-Alive / 浏览器连接复用
HTTP/1.1 的 Keep-Alive 就是"TCP 连接用完不断开，下次请求复用"。本质思想一样。
类比在哪里失效：HTTP Keep-Alive 对前端开发者透明。数据库连接池需要后端精确配置： 连接数设少了 → 请求排队等连接超时；设多了 → 数据库端连接数超限。 连接泄漏（借了连接忘了还）是后端常见的线上事故——所有请求都卡在"等待获取连接"。
不掌握会踩的坑： ① 连接泄漏：事务没提交/没关闭 → 连接一直被占用 → 池耗尽 → 全站挂掉。 ② 默认连接池大小（10 个）扛不住流量 → 需要根据并发量和数据库承受能力调整。 ③ 在事务里做了 HTTP 调用等耗时操作 → 连接被长时间占用 → 连接池快速耗尽。

运行时层 · 06

序列化与反序列化

把 Java 对象变成可传输/存储的格式（JSON/字节流），以及反向转换

概念与问题

前端 JSON.stringify() / JSON.parse() 就是序列化/反序列化。 但 Java 世界里这件事复杂得多：除了 JSON（用 Jackson 库），还有 Java 原生二进制序列化、Protobuf、 以及各种框架对序列化行为的深度控制（字段命名策略、日期格式、null 处理、循环引用等）。

Java 代码示例
// Jackson：Spring Boot 默认 JSON 序列化库
public class UserVO {
    private String name;

    @JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")
    private LocalDateTime createdAt;

    @JsonIgnore  // 序列化时忽略此字段（不返给前端）
    private String passwordHash;

    @JsonProperty("user_name")  // JSON key 用 snake_case
    public String getName() { return name; }
}

// Spring Boot Controller 自动用 Jackson 把返回值转成 JSON
@GetMapping("/user")
public UserVO getUser() {
    return new UserVO("Alice", LocalDateTime.now(), "xxx");
}
// 响应体：{"user_name":"Alice","createdAt":"2026-08-19 10:00:00"}
// passwordHash 被 @JsonIgnore 过滤掉了
前端类比：JSON.stringify() / JSON.parse()
功能完全一样——把对象变成字符串 / 把字符串变回对象。
类比在哪里失效：JS 的 JSON 处理几乎是"傻瓜式"的——对象结构和 JSON 天然一致。 Java 是强类型语言，反序列化时必须有目标类型：JSON 字符串 "123" 要变成 Long 还是 String？ 日期字符串用什么格式解析？嵌套对象的泛型怎么处理？这些问题都需要通过注解或全局配置来精确控制。 此外 Java 还有二进制序列化（用于 RPC、缓存），效率高但不可读——这在前端完全不存在。
不掌握会踩的坑： ① 日期字段前端收到的格式不对（时间戳 vs 字符串）——因为没配 @JsonFormat 或全局日期格式化。 ② 循环引用导致序列化死循环 / 栈溢出（User → Orders → User → ...）。 ③ 反序列化时类型不匹配直接报错，而前端因为弱类型从不会遇到这个问题。

运行时层 · 07

类加载机制 (ClassLoader)

Java 的"代码是怎么被加载到内存里的"——一套层级委托机制

概念与问题

JavaScript 用 import / require() 加载模块，由打包工具（Vite/Webpack）在编译时处理。 Java 的类加载发生在运行时：JVM 第一次使用某个类时，由 ClassLoader 将 .class 文件加载到内存。 类加载遵循双亲委派模型——先让父加载器加载，父加载器加载不了再自己加载，以此保证核心类库不被篡改。

Java 代码示例
// 双亲委派模型的三层结构
// Bootstrap ClassLoader  → 加载 java.lang.* 等核心类 (JDK 自带)
//   ↑ 委托
// Extension ClassLoader  → 加载 JDK 扩展库
//   ↑ 委托
// Application ClassLoader → 加载你写的业务代码和第三方 JAR

// 查看某个类是由哪个 ClassLoader 加载的
System.out.println(String.class.getClassLoader());
// → null（Bootstrap ClassLoader，C++ 实现）

System.out.println(UserService.class.getClassLoader());
// → jdk.internal.loader.ClassLoaders$AppClassLoader

// 热部署原理：DevTools 用新的 ClassLoader 重新加载修改过的类
// 所以 Spring Boot DevTools 改代码不用重启就能生效
前端类比：ESM 的 import / Webpack 的模块解析
前端也有模块加载和解析规则（node_modules 查找、别名路径解析）。
类比在哪里失效：前端模块加载在编译时由打包工具静态分析完成，运行时已经是打包后的代码。 Java 的类加载是运行时动态发生的——JVM 启动后按需加载类。这导致了一些前端不存在的问题： 同一个类被不同 ClassLoader 加载两次 → JVM 认为是两个不同的类 → 类型转换异常。 这在前端世界完全无法想象。
不掌握会踩的坑： ① ClassNotFoundException / NoClassDefFoundError 区别不清楚——前者是找不到类文件， 后者是类文件存在但加载时出错（比如静态初始化块抛异常）。 ② 在 Tomcat 等容器中部署多个应用，两个应用各自加载了同一个类的不同版本 → 诡异的类型转换错误。

运行时层 · 08

阻塞 I/O vs 非阻塞 I/O

前端天生异步无阻塞，后端默认是"同步阻塞"的——这决定了并发模型的根本差异

概念与问题

前端调 fetch() 是异步的——发出请求后 JS 主线程继续执行其他代码，响应回来时触发回调。 而 Java Spring Boot（默认 Spring MVC）是同步阻塞的：每个请求占用一个线程， 调数据库 / 调下游 API 时，这个线程就阻塞等待，什么都不做直到结果返回。

这意味着 Spring MVC 的并发能力受限于线程数（默认 200）。 如果想实现类似 Node.js 的非阻塞模型，需要用 Spring WebFlux（响应式编程）。

Java 代码示例
阻塞模型（Spring MVC，默认）
@GetMapping("/order")
public Order getOrder(Long id) {
    // 线程阻塞等待数据库响应
    Order o = orderDao.findById(id);
    // 线程继续阻塞等待 HTTP
    User u = restTemplate
        .getForObject(userUrl, User.class);
    o.setUser(u);
    return o;
    // 整个过程线程被占用
}
非阻塞模型（Spring WebFlux）
@GetMapping("/order")
public Mono<Order> getOrder(Long id) {
    // 类似 Promise 链式调用
    return orderRepo.findById(id)
        .flatMap(o ->
            webClient.get()
                .uri(userUrl)
                .retrieve()
                .bodyToMono(User.class)
                .map(u -> {
                    o.setUser(u);
                    return o;
                })
        );
    // 线程不阻塞，事件驱动
}
前端类比：async/await + 事件循环
JavaScript 的 await fetch() 看起来是"等待"，但实际上 JS 主线程并没有阻塞——只是语法糖把异步回调写成了同步形式。 Spring WebFlux 的 Mono/Flux 就类似 Promise。
类比在哪里失效：① 前端天生只有一种模型（异步非阻塞），没有选择题。后端需要在阻塞和非阻塞之间做架构决策。 ② Spring MVC（阻塞模型）是 Java 后端的绝对主流，大多数项目都在用——非阻塞反而是少数派。 ③ Java 的阻塞 I/O 可以靠"加线程"来扩展并发（200 线程就是 200 并发），和 Node.js 单线程事件循环是完全不同的并发哲学。
不掌握会踩的坑： ① 在 Spring MVC 里调一个慢接口（5 秒响应），那个线程就被白白占用 5 秒 → 200 个线程很快耗尽 → 新请求全部排队。 ② 前端思维里"调接口不阻塞当前执行"，在后端默认不是这样——不知道 @Async 或 WebFlux 就没法做异步。 ③ 混用阻塞和非阻塞代码（比如在 WebFlux 里调了 JDBC 阻塞方法）→ 性能反而更差。
