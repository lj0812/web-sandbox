典型场景：接口签名方案

客户端（Web / 安卓 / iOS）请求后端接口时，如何防止接口被黑客随意调用

场景与威胁模型

App 上线后，接口地址是公开的（抓包即可拿到）。后端需要回答一个问题：这个请求是不是我们官方客户端发的？有没有被改过？典型的攻击手段有：

攻击说明签名如何防御
参数篡改抓包后把 amount=1 改成 amount=0.01 再发出签名覆盖所有参数，改任何一个值签名就不匹配
重放攻击把抓到的合法请求原样再发一次（如重复下单、重复领券）签名中加入时间戳 + 随机数（nonce），同一签名只能用一次
脚本批量调用脱离客户端用脚本刷接口（薅羊毛、爬数据）签名密钥只存在于客户端与服务端，拿不到密钥就伪造不出合法签名

先想清楚防谁：签名能防「没有密钥的第三方」，防不了「逆向了 App 拿到密钥的黑客」。它的定位是大幅提高攻击成本 + 保证传输完整性，配合风控、限流、人机验证形成纵深防御，而不是银弹。

整体流程

客户端：参数 + timestamp + nonce ──排序拼接──> 待签名串 ──HMAC(secretKey)──> sign
请求：参数 + timestamp + nonce + sign ──────────────> 服务端
服务端：用同样规则重算签名 ──比对──> 一致放行 / 不一致拒绝

核心思想：密钥（secretKey）不参与网络传输，传输的只有签名结果。黑客抓包只能看到 sign，没有密钥就改不了参数、也造不出新签名。

客户端要做的工作

1. 获取并保管密钥

  • 每个客户端（或每个用户）分配一对 appKey / secretKey：appKey 标识身份、随请求明文传输；secretKey 用于签名、绝不出现在网络上
  • Web 端：secretKey 不能硬编码，通常登录后由服务端按用户下发，与登录态绑定并可过期
  • 安卓 / iOS：密钥可内置（配合混淆、so 库存储提高逆向成本），更稳妥的方案也是登录后动态下发

2. 构造待签名串

// 1. 收集所有业务参数（不含 sign 本身、通常不含文件二进制）
const params = {
  appKey: 'app_001',
  orderId: '20260824001',
  amount: '100',
  timestamp: String(Date.now()),          // 毫秒时间戳，防重放
  nonce: crypto.randomUUID(),             // 随机串，防重放
};

// 2. 按参数名 ASCII 排序后拼接成 k=v&k=v 形式（规则前后端必须逐字一致）
const signStr = Object.keys(params)
  .sort()
  .map(k => `${k}=${params[k]}`)
  .join('&');
// amount=100&appKey=app_001&nonce=xxx&orderId=...&timestamp=...

排序是为了让两端对同一组参数得到唯一确定的字符串，不受字段顺序影响。

3. 计算签名并发起请求

// 3. 用 secretKey 对待签名串计算 HMAC-SHA256（算法见 哈希与 HMAC 篇）
const sign = await hmacSha256(secretKey, signStr);

// 4. 签名放入请求头（或请求参数），连同时间戳、nonce 一起发出
fetch('/api/order', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-App-Key': 'app_001',
    'X-Timestamp': params.timestamp,
    'X-Nonce': params.nonce,
    'X-Sign': sign,
  },
  body: JSON.stringify({ orderId: '20260824001', amount: '100' }),
});

实际项目通常把以上逻辑封装在请求拦截器（如 axios interceptor）里，业务代码无感知。

细节决定成败：URL 编码与否、空值参数是否参与、value 是否统一转字符串、GET 的 query 和 POST 的 body 是否都参与签名——任何一处与后端不一致都会验签失败。规则必须写进联调文档并逐条对齐。

服务端要做的工作

1. 重算签名并比对

  • 从请求中取出 appKey，查出对应的 secretKey
  • 按与客户端完全相同的规则重构待签名串，重算 HMAC
  • 用恒定时间比较（防计时攻击）比对两个签名，不一致直接拒绝

2. 防重放校验

  • 时间戳：与服务器时间偏差超过窗口（如 ±5 分钟）即拒绝，防止旧请求被延迟重放
  • nonce：把窗口期内已使用的 nonce 存入 Redis（过期时间 = 时间窗口），重复出现即拒绝，保证同一签名只能用一次

3. 配套管理

  • 密钥管理：secretKey 的生成、存储（服务端加密存储）、按 appKey 轮换、泄露后的吊销
  • 通道隔离：Web / Android / iOS 可用不同 appKey，某一端密钥泄露时单独吊销
  • 灰度与兼容：签名算法升级（如 MD5 → HMAC-SHA256）时，按版本号并行支持新旧规则
  • 审计日志：验签失败打点告警，大量失败通常意味着攻击或客户端 bug

完整时序

① 登录/启动：客户端从服务端获取 secretKey（与登录态绑定）
② 每次请求：参数 + timestamp + nonce → 排序拼接 → HMAC → sign
③ 传输：明文参数 + sign（走 HTTPS）
④ 服务端：校验时间戳窗口 → 校验 nonce 未用 → 重算签名比对 → 记录 nonce → 执行业务

常见变体与升级

方案说明适用
HMAC 对称签名本文主方案，实现简单自家客户端 ↔ 自家服务端，绝大多数业务
RSA/ECDSA 非对称签名客户端持私钥签名，服务端持公钥验签；私钥泄露影响面更可控开放平台、对安全性要求更高的金融场景
签名串加入 body 摘要大 body 不参与拼接，改为拼入 sha256(body)请求体较大或含复杂 JSON 的接口
设备指纹 + 风控签名之外叠加设备标识、行为风控、滑块验证被薅羊毛严重的营销、领券类接口

速记

  • 签名 = 排序拼接（参数 + 时间戳 + nonce）→ HMAC(secretKey)；密钥不上网，传输的只有结果。
  • 时间戳防「延迟重放」，nonce 防「窗口内重放」，两者缺一不可。
  • 客户端难点是密钥保管与规则对齐；服务端难点是验签、防重放与密钥生命周期管理。
  • 签名防不了已逆向客户端的攻击者，它是抬高成本的闸门，要和 HTTPS、风控配合使用。
