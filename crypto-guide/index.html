1.基础概念

先分清编码、哈希、加密这三件经常被混为一谈的事。

编码 ≠ 哈希 ≠ 加密

日常开发里说的「加密」，很多时候其实不是加密。三者的本质区别在于：是否可逆、是否需要密钥。

编码（Encoding）哈希（Hash）加密（Encryption）
目的数据格式转换，便于传输/存储生成数据指纹，校验完整性保护数据机密性
是否可逆可逆（解码）不可逆（理论上）可逆（解密）
是否需要密钥不需要不需要（HMAC 需要）需要
常见例子Base64、URL 编码、UnicodeMD5、SHA-256AES、RSA

常见误区：Base64 不是加密！它只是把二进制数据转成可打印字符，任何人都能解码。把 Base64 后的密码当作「加密后的密码」是严重的安全问题。

编码（Encoding）

编码解决的是「数据怎么表示」的问题，不涉及任何安全性。

// Base64：浏览器原生 API
btoa('你好');              // 报错！btoa 只支持 Latin1 字符
btoa(unescape(encodeURIComponent('你好'))); // '5L2g5aW9' 中文要先转 UTF-8
atob('aGVsbG8=');         // 'hello'

// URL 编码：用于 query string
encodeURIComponent('a b&c'); // 'a%20b%26c'

Base64 常用于：在 JSON 中传输二进制（如图片 DataURL）、Basic Auth 的 Authorization 头、JWT 的各段编码（Base64URL）。

哈希（Hash）

哈希是单向函数：任意长度的输入 → 固定长度的输出（摘要/指纹）。理想特性：

  • 单向性：无法从摘要反推原文
  • 雪崩效应：输入改一个 bit，输出天差地别
  • 抗碰撞：极难找到两个不同输入得到相同输出

典型用途：密码存储（加盐哈希）、文件完整性校验（下载页给的 SHA-256）、接口签名、ETag。详见 哈希与 HMAC 一章。

加密：对称与非对称

对称加密非对称加密
密钥加密解密用同一把密钥公钥加密、私钥解密（或私钥签名、公钥验签）
速度快，适合大数据量慢（约慢 100~1000 倍），适合小数据
代表算法AES、（废弃的 DES/3DES）、SM4RSA、ECC、SM2
核心难题密钥如何安全地交给对方公钥如何确认是对方的（证书体系）

实际系统几乎都是「混合加密」：用非对称加密交换一把临时的对称密钥，之后的数据全部用对称加密传输。HTTPS/TLS 就是这样工作的。详见 混合加密。

核心术语

术语说明
密钥（Key）加密/解密的核心参数。AES-256 指密钥长度 256 bit。密钥强度决定安全性，算法本身都是公开的。
IV（初始化向量）让「相同明文 + 相同密钥」每次加密出不同密文的随机数。不需要保密，但必须每次随机生成、不可复用。详见 名词速查。
盐（Salt）哈希密码时混入的随机字符串，防止彩虹表攻击。与哈希结果一起存储，不需要保密。
填充（Padding）块加密要求明文长度是块大小的整数倍，不足部分按规则补齐，如 PKCS7。
摘要 / 指纹（Digest）哈希函数的输出结果。
签名（Signature）用私钥对摘要加密得到的结果，用于证明「消息来自私钥持有者且未被篡改」。详见 数字签名。

一句话总结：编码是翻译，谁都能看懂；哈希是指纹，只能比对不能还原；加密是保险箱，有钥匙才能打开。「可逆的哈希」「用 Base64 加密」这类说法，都是面试和 code review 中的危险信号。

2.哈希与 HMAC

常见哈希算法对比

算法输出长度现状前端还能不能用
MD5128 bit（32 位十六进制）已破解，存在碰撞攻击不能用于安全场景；做文件去重/缓存标识等非安全用途勉强可以
SHA-1160 bit已破解（Google 2017 年演示碰撞）同上，不要用于签名
SHA-256256 bit安全，当前主流可以，浏览器 Web Crypto 原生支持
SHA-512512 bit安全可以，同 SHA-256
SM3256 bit安全，国密标准政企/金融国产化项目使用

前端计算哈希：Web Crypto API

// 计算字符串的 SHA-256（浏览器原生，无需任何库）
async function sha256(text) {
  const data = new TextEncoder().encode(text);
  const digest = await crypto.subtle.digest('SHA-256', data);
  // ArrayBuffer → 十六进制字符串
  return [...new Uint8Array(digest)]
    .map(b => b.toString(16).padStart(2, '0'))
    .join('');
}

sha256('hello').then(console.log);
// 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824

注意：crypto.subtle 只在安全上下文（HTTPS 或 localhost）下可用。

// 计算文件的 SHA-256（如上传前秒传校验）
async function fileHash(file) {
  const buf = await file.arrayBuffer();
  const digest = await crypto.subtle.digest('SHA-256', buf);
  return [...new Uint8Array(digest)]
    .map(b => b.toString(16).padStart(2, '0'))
    .join('');
}

大文件配合分片读取计算，可以实现「秒传」：先传哈希，服务端发现已有相同内容就直接返回。

密码存储：为什么不能只用 SHA-256

密码不能加密存储（可逆 = 会泄露），只能存哈希。但直接 sha256(password) 仍然不安全：

  • 彩虹表：常见密码的哈希早已被人预先算好，查表即破
  • 相同密码哈希相同：泄露后能一眼看出哪些用户密码一样
  • SHA 太快：GPU 每秒可尝试数十亿次，暴力破解成本低

正确做法是加盐 + 慢哈希：

算法说明
bcrypt内置随机盐 + 可调计算成本，最常用
scrypt同时消耗 CPU 和内存，抗专用硬件
Argon22015 年密码哈希竞赛冠军，目前最推荐

前端的责任边界：密码哈希由服务端完成。前端可以做一层哈希再传输（避免明文出现在日志里），但这只是锦上添花，绝不能替代服务端哈希——否则哈希本身就变成了「密码」。

HMAC：带密钥的哈希

普通哈希只能校验「数据没被改」，但无法证明「数据是谁发的」——任何人都能重新算一个哈希。HMAC 把密钥混入哈希过程：

HMAC(key, message) = Hash( (key ⊕ opad) + Hash( (key ⊕ ipad) + message ) )

不知道密钥的人无法伪造合法的 HMAC，因此常用于接口签名（完整方案见 第 6 章）：

// 典型的开放接口签名流程
// 1. 拼接待签名串：参数排序 + 时间戳 + nonce
const signStr = 'appId=xxx&timestamp=1720000000&nonce=abc';

// 2. 用分配的 secretKey 计算 HMAC-SHA256 作为签名
sign = HMAC_SHA256(secretKey, signStr);

// 3. 服务端用同样的规则验签；时间戳防重放，nonce 防重复提交

微信支付、阿里云等开放平台的 API 签名都是这个套路。

// Web Crypto 计算 HMAC-SHA256
async function hmacSha256(keyText, message) {
  const enc = new TextEncoder();
  const key = await crypto.subtle.importKey(
    'raw', enc.encode(keyText),
    { name: 'HMAC', hash: 'SHA-256' },
    false, ['sign']
  );
  const sig = await crypto.subtle.sign('HMAC', key, enc.encode(message));
  return [...new Uint8Array(sig)]
    .map(b => b.toString(16).padStart(2, '0'))
    .join('');
}

注意：HMAC 的密钥写在前端代码里等于公开。前端做 HMAC 签名的场景，secretKey 必须由后端动态下发（且通常与登录态绑定），不能硬编码。详见 密钥硬编码误区。

速记：校验完整性 → SHA-256；接口签名 → HMAC-SHA256；存密码 → bcrypt / Argon2（服务端的事）。MD5、SHA-1 已不安全，新代码不要再用于任何安全用途。哈希验「没被改」，HMAC 验「没被改 + 是自家人发的」。

3.对称加密 AES

AES 是什么

AES（Advanced Encryption Standard）是目前事实标准的对称加密算法，分组长度 128 bit，密钥长度可选 128 / 192 / 256 bit（即 AES-128 / AES-256）。

  • DES：56 bit 密钥，已被暴力破解，淘汰
  • 3DES：DES 的加强版，速度慢，淘汰
  • SM4：国密对称算法，政企项目使用

一次 AES 加密需要四个要素：密钥、工作模式、IV、填充方式。前后端对接时这四个必须完全一致，否则解不开。

工作模式：ECB / CBC / GCM

明文长度超过一个分组（16 字节）时，需要决定多个分组如何串联加密，这就是工作模式。

模式特点结论
ECB每个分组独立加密，相同明文块 → 相同密文块，会泄露数据规律（著名的「企鹅图」）禁止使用，但很多老接口还在用
CBC每个分组先与前一个密文块异或再加密，需要 IV可用，但只有机密性没有完整性校验，新系统建议 GCM
GCM加密同时生成认证标签（Tag），能发现密文被篡改（AEAD）推荐，TLS 1.3 唯一保留的模式类型

IV 的正确用法：每次加密用密码学随机数生成新 IV，然后把 IV 和密文一起传输（IV 不需要保密）。绝对不要固定 IV、不要在 CBC 里复用 IV——这会让模式的优势荡然无存。

前端写法一：crypto-js（CBC 示例）

import CryptoJS from 'crypto-js';

// 密钥和 IV 都是 16 字节（AES-128）；实际项目密钥由后端下发，不能硬编码
const key = CryptoJS.enc.Utf8.parse('0123456789abcdef');
const iv  = CryptoJS.enc.Utf8.parse('abcdef0123456789');

function encrypt(text) {
  const encrypted = CryptoJS.AES.encrypt(text, key, {
    iv,
    mode: CryptoJS.mode.CBC,
    padding: CryptoJS.pad.Pkcs7,
  });
  return encrypted.ciphertext.toString(CryptoJS.enc.Base64);
}

function decrypt(base64) {
  const cipherParams = CryptoJS.lib.CipherParams.create({
    ciphertext: CryptoJS.enc.Base64.parse(base64),
  });
  const decrypted = CryptoJS.AES.decrypt(cipherParams, key, {
    iv,
    mode: CryptoJS.mode.CBC,
    padding: CryptoJS.pad.Pkcs7,
  });
  return decrypted.toString(CryptoJS.enc.Utf8);
}

对接后端时最常见的坑：crypto-js 直接传字符串密钥时会被当作 passphrase 走 PBKDF2 派生，结果和后端对不上。要么前后端都用 parse 后的 WordArray，要么都用 passphrase 模式。

前端写法二：Web Crypto API（GCM 示例）

// AES-256-GCM：浏览器原生，无需第三方库
async function aesGcmEncrypt(text, rawKey) {
  const key = await crypto.subtle.importKey(
    'raw', rawKey, { name: 'AES-GCM' }, false, ['encrypt']
  );
  const iv = crypto.getRandomValues(new Uint8Array(12)); // GCM 推荐 12 字节 IV
  const cipherBuf = await crypto.subtle.encrypt(
    { name: 'AES-GCM', iv },
    key,
    new TextEncoder().encode(text)
  );
  // 输出：iv + 密文，打包后 Base64
  const packed = new Uint8Array(iv.length + cipherBuf.byteLength);
  packed.set(iv, 0);
  packed.set(new Uint8Array(cipherBuf), iv.length);
  return btoa(String.fromCharCode(...packed));
}

async function aesGcmDecrypt(base64, rawKey) {
  const packed = Uint8Array.from(atob(base64), c => c.charCodeAt(0));
  const iv = packed.slice(0, 12);
  const data = packed.slice(12);
  const key = await crypto.subtle.importKey(
    'raw', rawKey, { name: 'AES-GCM' }, false, ['decrypt']
  );
  const plainBuf = await crypto.subtle.decrypt({ name: 'AES-GCM', iv }, key, data);
  return new TextDecoder().decode(plainBuf);
}

密文被篡改时 decrypt 会直接抛错——这就是 GCM 的完整性保护。

前后端对接清单

解密对不上时，按这个顺序排查：

检查项常见不一致
密钥长度16 / 24 / 32 字节对应 AES-128 / 192 / 256；密钥是原始字节还是 Base64/Hex 后的
工作模式ECB / CBC / GCM；GCM 还要确认 Tag 长度和 IV 长度
IV固定还是每次随机；传输时拼在密文头部还是单独字段
填充Pkcs7 / NoPadding（NoPadding 要求明文长度对齐）
编码密文输出是 Base64 还是 Hex；明文输入的字符集（UTF-8）

速记：新项目用 AES-256-GCM；维护老接口遇到 ECB 时知道它不安全，但对接时该用还得用。IV 每次随机、随密文传输；密钥才是要保密的部分。密钥硬编码在前端 = 没有加密。

4.非对称加密 RSA

核心思想

对称加密的死穴是「密钥怎么安全地给到对方」。非对称加密用一对数学上关联的密钥解决：

  • 公钥：可以公开给任何人
  • 私钥：自己保管，绝不外泄
方向用途效果
公钥加密 → 私钥解密保密传输只有私钥持有者能读懂内容
私钥签名 → 公钥验签身份认证 / 防抵赖证明内容确实来自私钥持有者且未被篡改

记忆口诀：公钥加密、私钥签名。加密是为了「只让你看」，签名是为了「证明是我发的」。

常见算法

算法基础说明
RSA大数分解难题最成熟通用；密钥较长（2048 bit 起步，1024 已不安全），加解密慢
ECC / ECDSA / Ed25519椭圆曲线离散对数同等安全强度下密钥短得多（256 bit ≈ RSA 3072 bit），区块链、现代系统常用
SM2椭圆曲线（国密）国家密码标准，政企、金融国产化项目必用

前端典型场景：RSA 加密敏感字段

很多登录接口要求「密码用 RSA 公钥加密后再提交」——即使 HTTPS 被代理抓包，抓到的也是密文：

import { JSEncrypt } from 'jsencrypt';

// 公钥由后端接口下发（可以公开），不要写死在代码里
const publicKey = await fetch('/api/public-key').then(r => r.text());

const encryptor = new JSEncrypt();
encryptor.setPublicKey(publicKey);

const encrypted = encryptor.encrypt(password); // Base64 密文
// 服务端用私钥解密得到原始密码

注意 RSA 加密的明文长度上限：2048 bit 密钥 + PKCS#1 v1.5 填充时，最多加密 245 字节。长数据要先截断、分段，或改用混合加密。

// 国密场景：sm-crypto（SM2 加密 / SM3 哈希 / SM4 对称加密）
import { sm2 } from 'sm-crypto';

const cipherText = sm2.doEncrypt(password, publicKey, 1); // 1 = C1C3C2 模式
const plainText  = sm2.doDecrypt(cipherText, privateKey, 1);

对接 SM2 时同样要确认 C1C3C2 / C1C2C3 顺序，这是国密对接最常见的坑。

混合加密：实战中的标准姿势

RSA 又慢又有长度限制，所以真实系统这样组合两种算法：

1. 前端随机生成一把 AES 会话密钥
2. 用 AES 加密业务数据
3. 用 RSA 公钥加密这把 AES 密钥
4. 一起发送：{ rsa加密的aes密钥, aes加密的业务数据 }

服务器用私钥解出 AES 密钥，再用它解密业务数据。这样兼得 RSA 的密钥分发能力和 AES 的速度。HTTPS/TLS 的握手也是同样思路。

公钥可信吗？证书体系

非对称加密还留了一个问题：你拿到的公钥怎么确定是对方的，而不是中间人替换的？答案是 数字证书：

  • 权威机构（CA）用自己的私钥对「域名 + 公钥」签名，生成证书
  • 浏览器内置 CA 的根证书（公钥），逐级验证证书链
  • 验证通过 → 公钥确实属于这个域名 → 建立安全连接

这就是为什么 Charles/Fiddler 抓 HTTPS 包需要手动安装并信任它的根证书——你在授权它扮演中间人。

速记：公钥加密、私钥签名；RSA 只能加密很短的数据，长数据走混合加密。RSA 至少 2048 bit；追求短密钥用 ECC；国产化项目用 SM2。公钥本身可以公开，但要靠证书体系防止被调包。

5.JWT 与数字签名

签名不是加密：看懂 JWT 的结构，明白它防什么、不防什么。

数字签名：先哈希，再用私钥「加密」

数字签名解决两个问题：消息是谁发的（认证）和消息有没有被改（完整性）。流程：

签名 = 私钥加密( Hash(原始消息) )
验签 = 公钥解密(签名) 的结果 与 Hash(收到的消息) 比对

只要比对一致，就说明消息确实由私钥持有者签发、且传输中未被篡改。常见签名算法：RSA（RS256）、ECDSA（ES256）、HMAC（HS256，对称签名）。

JWT 的结构：三段式

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
eyJ1c2VySWQiOjEwMDEsImV4cCI6MTcyMDAwMDAwMH0
.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Header（算法声明） . Payload（业务数据） . Signature（签名），每段都是 Base64URL 编码。

// 前端解析 JWT 的 payload（不需要任何库）
function parseJwt(token) {
  const payload = token.split('.')[1];
  // Base64URL → Base64：补回 - _ / + 和填充
  const base64 = payload.replace(/-/g, '+').replace(/_/g, '/');
  return JSON.parse(decodeURIComponent(escape(atob(base64))));
}

parseJwt(token); // { userId: 1001, exp: 1720000000 }

常用于前端判断 token 是否过期（exp）、读取用户角色做界面展示。

最重要的一条认知：JWT 没有加密！Header 和 Payload 只是 Base64 编码，任何人都能解码看到内容（在 jwt.io 粘贴即可）。签名保证的是「不能伪造、不能篡改」，不是「别人看不到」。所以 JWT 里永远不要放密码、身份证号等敏感信息。

签名算法怎么选

算法类型适用场景
HS256（HMAC-SHA256）对称：签发和验签用同一个 secret单体应用，只有自己的服务端验签
RS256（RSA）非对称：私钥签发，公钥验签微服务 / 第三方验签：公钥可以随便发，私钥只有认证中心持有
ES256（ECDSA）非对称，椭圆曲线同 RS256，但签名更短、更快

alg: none 攻击：早期一些 JWT 库允许算法声明为 none（不验签），攻击者改算法头即可伪造 token。现代库已默认拒绝，但服务端必须白名单指定算法，不能信任 token 头里的 alg 字段——这也是 RS256 token 被降级篡改成 HS256（用公钥当 HMAC 密钥）攻击的防御方式。

前端使用 JWT 的注意事项

问题说明
存哪localStorage 方便但怕 XSS（JS 可读取即被盗）；HttpOnly Cookie 防 XSS 但要防 CSRF。没有银弹，配合 XSS/CSRF 防护整体考虑
怎么带通常放在请求头：Authorization: Bearer <token>
过期怎么办短时效 access token + 长时效 refresh token；前端在 401 时用 refresh token 静默换新
能撤销吗JWT 本身无状态、签发后无法撤回；需要「退出登录立即失效」时要靠服务端黑名单或缩短有效期

速记：签名验「真伪与完整」，不管「保密」；JWT 是编码 + 签名，不是加密。Payload 任何人可读，别放敏感数据。验签密钥永远在服务端，前端只负责存储、携带和解析。

6.典型场景：接口签名方案

客户端（Web / 安卓 / iOS）请求后端接口时，如何防止接口被黑客随意调用。

场景与威胁模型

App 上线后，接口地址是公开的（抓包即可拿到）。后端需要回答一个问题：这个请求是不是我们官方客户端发的？有没有被改过？典型的攻击手段有：

攻击说明签名如何防御
参数篡改抓包后把 amount=1 改成 amount=0.01 再发出签名覆盖所有参数，改任何一个值签名就不匹配
重放攻击把抓到的合法请求原样再发一次（如重复下单、重复领券）签名中加入时间戳 + 随机数（nonce），同一签名只能用一次
脚本批量调用脱离客户端用脚本刷接口（薅羊毛、爬数据）签名密钥只存在于客户端与服务端，拿不到密钥就伪造不出合法签名

先想清楚防谁：签名能防「没有密钥的第三方」，防不了「逆向了 App 拿到密钥的黑客」。它的定位是大幅提高攻击成本 + 保证传输完整性，配合风控、限流、人机验证形成纵深防御，而不是银弹。

整体流程

客户端：参数 + timestamp + nonce ──排序拼接──> 待签名串 ──HMAC(secretKey)──> sign
请求：参数 + timestamp + nonce + sign ──────────────> 服务端
服务端：用同样规则重算签名 ──比对──> 一致放行 / 不一致拒绝

核心思想：密钥（secretKey）不参与网络传输，传输的只有签名结果。黑客抓包只能看到 sign，没有密钥就改不了参数、也造不出新签名。

客户端要做的工作

1. 获取并保管密钥

  • 每个客户端（或每个用户）分配一对 appKey / secretKey：appKey 标识身份、随请求明文传输；secretKey 用于签名、绝不出现在网络上
  • Web 端：secretKey 不能硬编码，通常登录后由服务端按用户下发，与登录态绑定并可过期
  • 安卓 / iOS：密钥可内置（配合混淆、so 库存储提高逆向成本），更稳妥的方案也是登录后动态下发

2. 构造待签名串

// 1. 收集所有业务参数（不含 sign 本身、通常不含文件二进制）
const params = {
  appKey: 'app_001',
  orderId: '20260824001',
  amount: '100',
  timestamp: String(Date.now()),          // 毫秒时间戳，防重放
  nonce: crypto.randomUUID(),             // 随机串，防重放
};

// 2. 按参数名 ASCII 排序后拼接成 k=v&k=v 形式（规则前后端必须逐字一致）
const signStr = Object.keys(params)
  .sort()
  .map(k => `${k}=${params[k]}`)
  .join('&');
// amount=100&appKey=app_001&nonce=xxx&orderId=...&timestamp=...

排序是为了让两端对同一组参数得到唯一确定的字符串，不受字段顺序影响。

3. 计算签名并发起请求

// 3. 用 secretKey 对待签名串计算 HMAC-SHA256（算法见第 2 章）
const sign = await hmacSha256(secretKey, signStr);

// 4. 签名放入请求头（或请求参数），连同时间戳、nonce 一起发出
fetch('/api/order', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-App-Key': 'app_001',
    'X-Timestamp': params.timestamp,
    'X-Nonce': params.nonce,
    'X-Sign': sign,
  },
  body: JSON.stringify({ orderId: '20260824001', amount: '100' }),
});

实际项目通常把以上逻辑封装在请求拦截器（如 axios interceptor）里，业务代码无感知。

细节决定成败：URL 编码与否、空值参数是否参与、value 是否统一转字符串、GET 的 query 和 POST 的 body 是否都参与签名——任何一处与后端不一致都会验签失败。规则必须写进联调文档并逐条对齐。

服务端要做的工作

1. 重算签名并比对

  • 从请求中取出 appKey，查出对应的 secretKey
  • 按与客户端完全相同的规则重构待签名串，重算 HMAC
  • 用恒定时间比较（防计时攻击）比对两个签名，不一致直接拒绝

2. 防重放校验

  • 时间戳：与服务器时间偏差超过窗口（如 ±5 分钟）即拒绝，防止旧请求被延迟重放
  • nonce：把窗口期内已使用的 nonce 存入 Redis（过期时间 = 时间窗口），重复出现即拒绝，保证同一签名只能用一次

3. 配套管理

  • 密钥管理：secretKey 的生成、存储（服务端加密存储）、按 appKey 轮换、泄露后的吊销
  • 通道隔离：Web / Android / iOS 可用不同 appKey，某一端密钥泄露时单独吊销
  • 灰度与兼容：签名算法升级（如 MD5 → HMAC-SHA256）时，按版本号并行支持新旧规则
  • 审计日志：验签失败打点告警，大量失败通常意味着攻击或客户端 bug
完整时序
① 登录/启动：客户端从服务端获取 secretKey（与登录态绑定）
② 每次请求：参数 + timestamp + nonce → 排序拼接 → HMAC → sign
③ 传输：明文参数 + sign（走 HTTPS）
④ 服务端：校验时间戳窗口 → 校验 nonce 未用 → 重算签名比对 → 记录 nonce → 执行业务

常见变体与升级

方案说明适用
HMAC 对称签名本文主方案，实现简单自家客户端 ↔ 自家服务端，绝大多数业务
RSA/ECDSA 非对称签名客户端持私钥签名，服务端持公钥验签；私钥泄露影响面更可控开放平台、对安全性要求更高的金融场景
签名串加入 body 摘要大 body 不参与拼接，改为拼入 sha256(body)请求体较大或含复杂 JSON 的接口
设备指纹 + 风控签名之外叠加设备标识、行为风控、滑块验证被薅羊毛严重的营销、领券类接口

速记：签名 = 排序拼接（参数 + 时间戳 + nonce）→ HMAC(secretKey)；密钥不上网，传输的只有结果。时间戳防「延迟重放」，nonce 防「窗口内重放」，两者缺一不可。签名防不了已逆向客户端的攻击者，它是抬高成本的闸门，要和 HTTPS、风控配合使用。

7.前端实战与常见误区

最大的误区：把密钥写在前端代码里

前端代码对用户完全透明——查看源码、抓包、断点调试都能拿到。任何硬编码在前端的密钥，都等同于公开。代码混淆、打包压缩只能增加几分钟的阅读成本，不构成安全。

那么「前端 AES 加密请求参数」这类需求还有没有意义？分场景看：

场景是否有意义
防普通抓包工具的直接阅读（运营、测试同学）有一定意义，属于「防君子不防小人」的遮挡
防中间人窃取敏感信息没有意义——密钥和密文一起在网络里，也一起在源码里
防恶意攻击者基本无效，攻击者会逆向、会 hook 加密函数

结论：前端加密是提高攻击成本的辅助手段，真正的机密性必须依靠 HTTPS，真正的敏感逻辑必须放在服务端。

密钥的正确来源

  • RSA 公钥：由后端接口下发，本来就可以公开，放前端没问题
  • AES 会话密钥：前端随机生成 → 用 RSA 公钥加密后传给服务端（混合加密，见 第 4 章）
  • HMAC secretKey：登录后由服务端按用户下发，与登录态绑定、可过期
  • 永远不该出现在前端的：RSA 私钥、固定的 AES 密钥、接口签名用的全局 secret

HTTPS 才是地基

前端加解密的一切讨论都建立在 HTTPS 之上。TLS 握手（简化版）：

1. 浏览器验证服务器证书（确认公钥归属）
2. 双方协商生成会话密钥（非对称加密 / DH 交换）
3. 之后所有数据用会话密钥做对称加密传输

有了 HTTPS，请求体在传输层已经是密文。业务层再加密的收益主要是：防内网明文日志、防代理层（网关）看到明文、满足合规要求——而不是防中间人。

Charles / Fiddler 能抓 HTTPS，是因为你主动安装并信任了它的根证书，授权它做中间人。普通用户不装证书，第三方就无法解密流量。

前端能用的库

库 / API用途说明

crypto-jsMD5 / SHA / AES(ECB/CBC)老项目常用；已停止维护，新项目建议 Web Crypto 或 noble 系

高频面试题速答

1. MD5 是加密吗？不是。MD5 是哈希（摘要）算法，单向不可逆。它只是常被口语误称为「MD5 加密」。

2. 前后端交互怎么保证数据安全？传输层靠 HTTPS；业务层敏感字段可用 RSA/混合加密；接口用 HMAC 签名 + 时间戳 + nonce 防篡改和重放；密码前端可先做哈希但服务端必须加盐慢哈希存储。

3. JWT 安全吗？JWT 只有签名没有加密，payload 明文可见。安全与否取决于：HTTPS 传输、不放敏感数据、服务端正确验签（固定算法白名单）、合理设置过期时间。

4. AES 的 ECB 和 CBC 有什么区别？ECB 每个块独立加密，相同明文块产生相同密文块，会泄露模式，禁止使用；CBC 引入 IV 和链式异或，相同明文每次加密结果不同。

5. 为什么有了 HTTPS 还要对密码 RSA 加密？HTTPS 保护「浏览器到服务器」的链路；但请求会经过网关、日志系统、反向代理等环节，明文密码可能落盘。应用层加密确保只有持有私钥的业务服务能看到明文。

一页纸总结：机密性——HTTPS 是地基，应用层加密防的是链路上游环节，密钥绝不能硬编码；完整性 + 来源认证——HMAC 签名或 RSA/ECDSA 签名；密码——前端顶多预哈希，存储必须是服务端加盐慢哈希；选型——哈希用 SHA-256，加密用 AES-256-GCM，非对称用 RSA-2048 / ECC，国密场景 SM2/SM3/SM4。记住三件事不能混：编码（Base64）、哈希（SHA）、加密（AES/RSA）。

8.名词速查表

阅读资料 / 对接后端时高频出现的名词，按主题分组。

向量类：IV / nonce / salt

加密语境里的 vector（向量），特指 IV（Initialization Vector，初始化向量）。三者都是「参与计算但保密性要求较弱」的随机数据，作用各不相同，最容易混淆。

名词全称 / 含义要不要保密能不能复用典型用途
IV Initialization Vector，初始化向量 不保密，随密文一起传输 绝不复用，每次加密重新随机 CBC/GCM 等模式，让相同明文每次加密出不同密文
nonce number used once，只用一次的数 不保密 绝不复用 接口签名防重放；GCM 模式下 nonce ≈ IV
salt（盐） 哈希密码时混入的随机字符串 不保密，与哈希值一起存储 每个用户一个，可长期不变 防彩虹表，见 密码存储

IV 复用 = 灾难。GCM 模式下，同一个密钥 + 同一个 nonce 加密两条不同明文，攻击者可直接恢复密钥和明文（这是 GCM 最经典的翻车姿势）。所以生成 IV 必须用密码学随机数，不能写死、不能用自增序号。

随机数

名词说明
PRNGPseudo-Random Number Generator，伪随机。如 Math.random()，可预测，不能用于安全场景。
CSPRNGCryptographically Secure PRNG，密码学安全伪随机。浏览器用 crypto.getRandomValues()、Node 用 crypto.randomBytes()。生成密钥 / IV / nonce 必须用它。
entropy（熵）随机性 / 不可预测程度的度量。熵越高越难猜。生成密钥、盐、nonce 都要求高熵来源。
// 生成 16 字节随机 IV（密码学安全）
const iv = crypto.getRandomValues(new Uint8Array(16));

// 生成随机 nonce 字符串
const nonce = crypto.randomUUID();

块与填充

名词说明
block（分组/块）块密码一次处理的固定长度数据。AES 分组长度恒为 128 bit（16 字节），与密钥长度无关。
block cipher（块密码）按固定块处理的算法，如 AES。明文不足整数块时需要填充。
stream cipher（流密码）逐字节 / 逐位处理的算法，如 ChaCha20。无需填充。
padding（填充）把明文补齐到块大小整数倍的方式。常用 PKCS7（每字节值 = 填充字节数）。GCM 等流式模式通常 NoPadding。

密钥相关

名词说明
key length（密钥长度）AES-128 / 192 / 256 指密钥位数，即 16 / 24 / 32 字节。越长越安全，速度略慢。
session key（会话密钥）一次连接内临时使用的对称密钥，用完即弃。HTTPS 每次连接都会协商新的会话密钥。
KDF（Key Derivation Function）密钥派生函数：从一个密码 / 主密钥派生出加密密钥。常见 PBKDF2、scrypt、Argon2。存密码和「用口令加密文件」都用它。
key wrapping（密钥包装）用一把密钥加密另一把密钥（混合加密里 RSA 加密 AES 密钥就是典型）。

加密模式与完整性

名词说明
AEADAuthenticated Encryption with Associated Data，带认证的加密。加密同时提供完整性校验，GCM、ChaCha20-Poly1305 属此类。新系统首选。
Tag（认证标签）GCM 等 AEAD 模式输出的校验值，验证密文未被篡改。解密时一并校验。
cipher suite（加密套件）TLS 握手协商的一组算法组合，如 TLS_AES_256_GCM_SHA384 = 对称算法 + 哈希。
forward secrecy（前向保密 / PFS）即使长期私钥未来泄露，历史会话也无法解密。靠每次会话用临时密钥（ECDHE）实现，现代 TLS 标配。

证书与信任

名词说明
CA（Certificate Authority）证书颁发机构，用私钥对证书签名，浏览器内置其根证书以建立信任。
certificate chain（证书链）从服务器证书逐级回溯到受信任根证书的路径。
fingerprint（指纹）证书内容的哈希值，用于人工核对证书是否被替换。
self-signed（自签名）用自己给自己签发的证书，不被浏览器默认信任，内网 / 开发环境常见。

常见攻击名词

攻击原理防御
brute force（暴力破解）穷举所有可能的密钥加大密钥长度 + 慢哈希
dictionary（字典攻击）用常见密码列表逐一尝试加盐 + 慢哈希 + 锁定策略
rainbow table（彩虹表）预先算好「密码→哈希」的查找表加盐使表失效
collision（碰撞攻击）构造两个不同输入得到相同哈希用抗碰撞算法（弃用 MD5/SHA-1）
birthday（生日攻击）利用生日悖论降低找碰撞的成本加大哈希输出长度
timing（计时攻击）通过比较耗时差异推断密钥/签名恒定时间比较
replay（重放攻击）原样重发截获的合法请求时间戳 + nonce，见 接口签名
MITM（中间人攻击）在通信双方之间拦截、篡改流量HTTPS + 证书校验 + 证书固定

编码 / 格式相关

名词说明
Base64 / Base64URL二进制转可打印文本。Base64URL 用 -_ 替代 +/、去掉填充 =，适合放 URL 和 JWT。
Hex（十六进制）每字节用两个 16 进制字符表示，哈希摘要常以 hex 展示。
PEM密钥 / 证书的文本封装格式，以 -----BEGIN ...----- 开头。
DER密钥 / 证书的二进制格式。
ArrayBuffer / Uint8ArrayWeb Crypto API 处理的二进制数据类型，加密前常需与字符串互转。

一句话速记：vector = IV——不保密、不复用、每次随机。IV / nonce 防「相同输入出相同结果」与重放；salt 防彩虹表。密钥、IV、nonce、盐一律用 crypto.getRandomValues() 生成，别用 Math.random()。新系统优先 AEAD（GCM / ChaCha20-Poly1305），自带完整性。
